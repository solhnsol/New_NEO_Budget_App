# Toss 결제·송금과 은행 알림 묶기 설계 (2026-10-23, 설계 단계 · 구현 전)

한 돈이 Toss 알림과 우리은행 알림으로 두 번 오는 두 가지 모양을 어떻게 한 건으로 볼지 정한다. 코드는 바꾸지 않았고, 현재 동작만 특성 테스트(`TossBankPairingCharacterizationTests`)로 고정했다. 테스트는 가짜 가게·금액만 쓴다. Toss 알림의 실제 문구는 이 설계에서 추정이므로, 구현 전에 실제 문구로 확인한다(아래 "열린 질문").

## 1. 지금 동작 (테스트로 확인)

| 모양 | 지금 결과 | 위험 |
|---|---|---|
| 1. Toss "N원이 결제됐어요"(계좌 언급 없음) + 우리 "[출금] 토스퀵계좌이체" | 두 알림 모두 원장에 못 오르고 검토 대기 2건. 서로 묶는 규칙 없음 | Toss 쪽에 "우리 계좌"로 답하고 출금 쪽도 확정하면 같은 지출이 두 번 잡힘 |
| 3. Toss 송금 "내 우리 계좌로 입금" + 우리 "[입금]" | 우리 입금이 수입 1건으로 오르고(잔액 +12,000), Toss 쪽은 이체 입금으로 검토 대기 1건. 어느 순서로 와도 같음 | 대기 건을 수입이나 이체로 확정하면 수입이 두 배 |

두 모양 모두 `NotificationCorrelator`의 규칙에 해당이 없다. `sameInstrumentAcrossProviders`는 두 알림이 같은 등록 계좌로 해소돼야 하는데 Toss 결제는 계좌를 말하지 않고, `walletTap`은 Wallet·현대카드 한 쌍 전용이며, `transferLegs`는 상대 계좌 키가 필요하다. 모양 2(Toss가 카드나 은행을 이름으로 말하는 결제)는 이미 계좌로 해소되어 기존 규칙으로 처리된다.

## 2. 제안 규칙

기존 판정 틀(`corroborates` / `closes`)과 `walletTap`의 방식을 그대로 따른다. 새 구조는 만들지 않는다. 구조적 근거는 "금액·시각"에 더해 **서로 상대를 가리키는 문구** 하나다.

### 규칙 A: `tossQuickPay` (Toss 결제 ↔ 우리 출금)
- 짝: Toss `tossPayment`(수단 미상, 즉 검토 대기) 하나와, 등록된 은행 계좌의 출금 알림 하나.
- 근거: 금액 같음 + 출금 상대 문구가 "토스"로 시작(토스퀵계좌이체, 토스 000 등) + 시각 차이 1분 이내(Hans: 실제 간격은 거의 동시. 1~10분은 제안).
- 결과: 지출 1건. 계좌는 출금 알림에서, 가게 이름은 Toss 알림에서 가져온다. 별도 출금 항목은 만들지 않는다.
- 도착 순서: 출금이 먼저면 출금은 검토 대기였다가 Toss 알림이 `closes`로 닫고 지출로 확정, Toss가 먼저면 출금이 `newAct`로 올라오며 Toss 대기를 닫는다. 어느 쪽이든 결과가 같아야 한다(24가지 순서 테스트 유지).
- 한 쪽에 한 쪽만 붙는다(`claimed`와 같은 방식). 같은 금액을 2분 안에 두 번 결제해도 쌍이 서로 엇갈려 붙지 않는다. 가장 가까운 시각, 같으면 ID가 작은 쪽.
- "토스" 문구가 없는 출금, 금액이 다른 출금은 묶지 않는다.

### 규칙 B: `tossDepositEcho` (Toss 송금 입금 ↔ 우리 입금)
- 짝: Toss `tossPersonDeposit`(은행만 말함)과, 같은 은행의 등록 계좌에 온 입금 알림.
- 근거: 금액 같음 + Toss가 말한 은행이 입금 계좌의 은행과 같음 + 시각 차이 1분 이내. 같은 은행 계좌가 둘 이상이어도 입금 알림이 계좌를 확정하므로 문제없다.
- 결과: 입금 1건(우리 알림이 대표). Toss 알림은 보조 근거로 남아 보낸 사람 이름을 채운다. 수입으로 보일지 이체로 볼지는 기존 정책(`docs/ledger-behavior.md`) 그대로다.
- 순서: 우리 입금이 먼저면 Toss 알림은 `corroborates`, Toss가 먼저면 우리 입금이 대기 중인 Toss 건을 `closes`로 닫는다.
- Toss가 은행 이름을 말하지 못한 경우는 묶지 않는다.

## 3. 예시 (가짜 값)

1. 19:13:30 Toss "12,000원이 결제됐어요 · 가상상점", 19:13:35 우리 "[출금] 토스퀵계좌이체 12,000원" → 지출 1건 12,000원, 생활비 계좌, 가게 "가상상점". 검토 대기 0건.
2. 반대 순서(출금 먼저)여도 같은 결과.
3. 19:13 Toss 결제 12,000원 · 19:14 Toss 결제 12,000원(같은 가게), 우리 출금 12,000원 한 번 → 지출 1건과 Toss 대기 1건. 어느 쪽이 짝인지는 시각이 가장 가까운 쪽, 남은 한 건은 지금처럼 계좌를 묻는다.
4. Toss 결제 12,000원, 우리 출금은 11,000원 또는 "토스" 문구 없음 → 묶지 않음. 지금처럼 각각 검토.
5. Toss 송금 "내 우리 계좌로 입금" 12,000원 + 우리 [입금] 12,000원 → 입금 1건. 보낸 사람은 Toss 알림 이름.

## 4. 이중 계상 위험과 안전 장치

- 문구가 안 맞아 묶지 못하는 경우는 지금과 같이 사용자에게 묻되, 검토 카드에서 **같은 금액·비슷한 시각의 기록이 이미 있으면** "이미 기록된 것과 같은 돈인가요?"를 먼저 보여주고 한 번 눌러 묶게 한다(`suggests`, 금액·시각만 맞는 짝은 제안일 뿐 자동 확정하지 않는다는 불변식 11 유지).
- 사용자가 Toss 대기 건에 계좌를 직접 답하는 순간, 같은 계좌에 같은 금액의 출금·입금 기록이 3분 안에 있으면 경고한다.
- 자동 묶음은 규칙 A, B처럼 문구와 은행이 모두 맞을 때만 한다. 하나라도 빠지면 위 제안으로 떨어진다.
- 사후 되돌리기: 잘못 묶인 쌍은 원장을 고치지 않고 근거 연결만 해제할 수 있어야 한다(기존 `corroborates` 해제 경로 확인 필요).

## 5. 구현 규모

- 규칙 A: 상호 추출 + 출금 문구 감지 + 상대 규칙 두 군데(corroborates, pendingClosed) + 테스트. 약 0.5~1일, Core 테스트만으로 검증 가능(클라우드).
- 규칙 B: 같은 방식, 약 0.5일.
- 검토 카드의 "같은 돈인가요?" 제안과 경고: SwiftUI 작업이라 노트북 확인이 필요, 약 0.5~1일.
- 합계 약 2일 안팎. 정책 확정 뒤 구현 스레드를 따로 연다.

## 6. 결정 (2026-10-23, Hans)

1. 문구·금액·시각이 모두 맞으면 묻지 않고 자동으로 묶는다.
2. 실제 간격은 거의 동시다. 자동 묶음 창을 **1분**으로 좁히고, 1분~10분 사이는 자동 확정하지 않고 "같은 돈인가요?" 제안으로 보낸다(예외 대비).
3. 우리 출금 문구는 "토스퀵계좌이체" 하나가 아니라 "토스 000"처럼 이름이 붙기도 한다. 그래서 문구 근거는 "토스로 시작하는 상대 이름"으로 넓힌다. 이 문구만으로는 친구 송금과 구별되지 않으므로, **대기 중인 Toss 결제 알림이 같은 금액으로 짝이 되는 경우에만** 묶는다(Toss 결제 알림이 결제임을 증명). 짝 없는 "토스 000" 출금은 지금처럼 묻는다.
