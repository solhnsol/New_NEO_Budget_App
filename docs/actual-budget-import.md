# Actual Budget 가계부 가져오기 설계

상태: **Q1–Q6 승인(2026-10-20, Hans), 구현됨(11절)**. 아래 1–10절은 승인받은 설계 그대로다. 금융 정책은 아래 예시로 합의한 뒤 구현한다(`docs/ledger-behavior.md`와 같은 방식). 이 문서에는 실제 금액·거래 내용을 쓰지 않았고, 예시는 모두 가상이다.

## 1. 결론

어렵지 않다. 다만 "알림으로 되돌려 넣기"가 아니라 **가져온 기록(imported)을 알림과 별도의 원장 입력으로 두는 방식**을 권한다. 규모가 작다.

## 2. 읽어 본 Actual 가계부 (읽기 전용, 개수만)

- 기록은 2026-09-30부터 10-19까지 약 3주, 거래 248건이다. 계좌는 급여통장·생활비·카카오페이·티머니·현대카드 MM(신용카드, 잔액이 마이너스)·한국투자증권(Off-budget) 6개다.
- 248건 중 157건은 알림에서 자동으로 들어온 것(`imported_payee`가 있음)이고 91건은 수동 입력·이체·정산·잔액 조정이다.
- 이체 60건은 30쌍이다(양쪽 모두 `transfer: "← 급여통장"` 같은 표시). 카테고리 없는 거래 65건, 정산 태그 거래 약 36건, `#데이트`·`#고정비` 등 태그 약 12건.
- `Starting Balances` 4건(티머니, 급여통장은 9/30에 금액이 있고 생활비는 1원짜리 2건). 현대카드 MM에는 시작 잔액이 없다. 그 잔액은 전부 가져올 기록으로 설명된다.
- 정산 입금은 원래 지출 카테고리에 양수로 들어가 있고, 메모에 `#정산 입금 · 원거래 <Actual 거래 id> · 입금거래 <id>`로 어느 지출을 갚았는지 남아 있다.
- 알림 원문도 서버에 보관되어 있다(`find_notifications`, 번호 약 340건, 본문 텍스트만). 시각은 한국시간 초 단위다.

## 3. OnAll이 지금 받을 수 있는 것

- 원장은 저장하지 않는다. `notifications.json`(받은 알림)과 `setup.json`(계좌 설정)만 저장하고 `IntakeLedger`가 알림을 순서대로 재생해 만든다(`docs/shortcut-intake.md`).
- 과거 기록을 넣는 길이 없다. 시작 잔액도 계좌 `openingBalance`만 있고 앱에는 입력하는 곳이 없다("0원부터 알림으로 움직인 만큼만 센다").
- `LedgerEntry`는 `evidenceIDs`로 근거를 붙이고 같은 근거를 두 번 쓰면 거부한다(`evidenceAlreadyUsed`). 이 성질을 가져온 기록의 중복 방지에 쓸 수 있다.
- 신용카드는 계좌가 아니라 `CreditInstrument`(부채)이고 시작 부채 필드가 없다. 현대카드는 9/30에 0에서 시작했으므로 지금은 필요 없지만, 이전 달 카드값이 남은 상태로 가져오려면 필요하다.

## 4. 선택지

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| A | Actual의 원문 알림을 앱의 알림 입력으로 다시 재생 | 새 경로 없음. 파서·Correlator가 그대로 일함 | 수동 입력(약 91건)·분류·정산 기록이 사라진다. 원문에 제목/부제가 없어 단축어가 보낸 알림과 해시(ID)가 달라 같은 알림이 두 번 들어갈 수 있다. 3주치뿐 |
| B | Actual 거래를 가져온 기록으로 변환해 별도 입력으로 저장 | 분류·태그·정산·수동 거래가 그대로 남는다. 알림 해시 문제 없음. 양방향 중복은 컷오버 한 곳에서만 처리 | 새 입력 파일 하나와 변환기가 필요하다 |
| C | B를 기본으로 하되, 컷오버 이후는 새 알림만 쓴다 | B와 같다 + 겹치는 구간을 하나의 규칙으로 닫는다 | 컷오버 날짜를 정해야 한다 |

**권장: C.** A는 Hans가 Actual에서 손으로 고친 것(분류, 정산 연결)을 버리므로 맞지 않는다.

## 5. 설계 (C)

### 5.1 데이터와 흐름

1. Actual 쪽: 읽기 전용 도구로 거래·계좌·카테고리를 내려받아 `imported-history.json`을 만든다(Actual은 바꾸지 않는다).
2. 파일은 git에 넣지 않는다. 저장소의 `data/`는 이미 무시되고, 변환기는 `tools/`에 코드만 둔다.
3. 앱은 `Application Support/Intake/imported-history.json`을 `notifications.json`, `setup.json` 옆에 읽는다. 원장은 계속 파생물이다: `IntakeLedger`가 **시작 잔액 → 가져온 기록 → 컷오버 이후 알림** 순서로 재생한다. 그래서 계좌 설정이 바뀌어도 다시 만들어진다.
4. 파일을 폰에 넣는 법은 아래 6절.

### 5.2 변환 규칙

| Actual | OnAll |
|---|---|
| 계좌 | 등록 계좌(카드는 `CreditInstrument`). 알림 계좌 확인 질문을 건너뛰도록 이름을 서로 맞춰 둔다 |
| `Starting Balances` | 그 계좌의 `openingBalance`(컷오버 직전 잔액이 아니라 Actual 시작 시점 값) |
| 지출/입금 | `LedgerEntry` expense / income. 시각은 날짜만 있어 그날 정오(KST)로 두고 "시각 미상" 표시를 단다 |
| 이체 쌍 | `transfer` 항목 하나(posting 두 개). 한쪽만 있으면 검토 |
| 카드 계좌로 가는 이체 | `cardPayment` |
| 잔액 조정 | `adjustment`가 아니라 시작 잔액 보정으로 모아 따로 보여 준다 |
| 카테고리·태그·메모 | 항목의 사용자 분류로 보관(분류 모델은 구현 때 확인) |
| 정산 입금(메모의 원거래 id) | 5.4절 |
| 근거 id | `evidenceIDs = ["actual:<거래 id>"]`. 다시 가져와도 중복되지 않는다 |

### 5.3 라이브 알림과의 겹침

컷오버를 "Actual에서 마지막으로 가져온 날의 다음 날 00:00 KST"로 둔다. 컷오버 전 시각의 알림은 원장에 넣지 않는다(이미 가져온 기록에 있다).

컷오버 당일 경계는 두 가지만 처리한다.

- 라이브 알림이 가져온 기록과 **같은 계좌·같은 금액·같은 날**이고 가져온 기록 쪽에 짝이 아직 없으면 `corroborates`(근거만 되고 새 항목은 만들지 않는다). 한 기록에는 알림 하나만 붙는다.
- 가져온 기록에서 한쪽만 있는 이체/카드 출금의 짝이 컷오버 뒤 알림으로 오면 기존 Correlator 규칙대로 닫는다.

가져온 기록끼리는 Correlator를 돌리지 않는다. Actual에서 이미 사람이 확정한 것이라 다시 판정하면 분류가 뒤집힐 수 있다.

### 5.4 정산·환불과 합산(netting) 정책과의 관계

`docs/ledger-behavior.md`의 원칙을 그대로 지킨다: **원장은 실제 부호 그대로, 합산은 표시만, 카드 실적은 긁은 금액 기준.**

- Actual의 정산 입금은 원래 지출 카테고리에 양수다. 그대로 원장에 넣으면 지출 합계가 줄어 보이므로(표시와 원장이 섞임) 입금은 `income`으로 넣고, 메모의 `원거래` id로 `Obligation` + `Settlement`를 만들어 연결한다. 그러면 기존 `LedgerList.netted`가 지출 줄에 붙여 순지출로 보여 준다.
- 사람 이름은 Actual에 없다(상호명 payee 규칙). 정산 상대는 "이름 없는 사람" 하나로 두고, 이후 앱에서 이름을 붙일 수 있게 한다.
- 입금 하나가 원거래 여러 개를 갚는 경우(메모에 `원거래`가 여러 개)는 Actual이 쪼갠 금액대로 `Settlement`를 나눈다.
- 카드 환불·취소(카드 계좌의 양수)는 `adjustment`(원거래 연결)로 넣고, 원거래를 못 찾으면 검토.
- 카드 실적은 가져온 지출도 gross로 센다. 정산 입금은 카드 쪽이 아니라 은행 쪽이라 영향이 없다.

## 6. 폰에 어떻게 넣나 (git에는 안 넣음)

권장: 클라우드 스레드가 Actual 도구로 변환 파일을 만들어 프로젝트 파일(비공개 프로젝트)에 두고, Hans가 내려받아 폰에 옮긴다(AirDrop → 파일 앱 → 앱의 "가져오기"로 선택). 앱에는 파일 선택 한 번과 "가져온 N건, 시작 잔액 M개" 확인 화면만 추가한다. 가져오기 뒤 프로젝트 파일에서 지운다.

대안: 노트북이 연결됐을 때 Remote Control로 폰에 직접 설치. 클라우드만으로는 폰 앱 저장소에 접근할 수 없다.

## 7. 개인정보

- 읽기 전용이다. Actual에 아무것도 쓰지 않는다.
- 파일은 git·커밋 메시지·PR에 들어가지 않는다. 문서와 테스트 데이터는 가상 거래만 쓴다.
- 폰에는 `completeFileProtectionUntilFirstUserAuthentication`으로 저장(기존 알림 저장과 같음).
- 정산 상대 이름은 Actual에 없어서 가져오지 않는다.

## 8. 작업량

| 일 | 규모 |
|---|---|
| 가져온 기록 모델 + `IntakeLedger` 재생 순서 + 컷오버/겹침 규칙 + 테스트 | 중간(한 스레드) |
| 변환기(`tools/`) + 가상 데이터 테스트 | 작음 |

## 9. 승인받을 예시 (가상 숫자)

**예시 1. 이체 쌍과 시작 잔액**
Actual: 급여통장 시작 100,000원. 10/5 급여통장 -20,000 / 티머니 +20,000(이체).
OnAll: 급여통장 `openingBalance` 100,000, 티머니 0. 10/5 `transfer` 한 건(급여통장 -20,000, 티머니 +20,000). 지출로 세지 않는다. 잔액은 급여통장 80,000, 티머니 20,000으로 Actual과 같다.

**예시 2. 정산 입금**
Actual: 10/6 현대카드 MM 식당 -60,000(식비). 10/7 생활비 계좌 입금 +30,000(식비, 메모 `#정산 입금 · 원거래 <식당 id>`).
OnAll: 식당은 `expense` 60,000(카드, 카드 실적 60,000). 입금은 `income` 30,000(은행)이고 `Settlement`로 식당에 연결. 가계부 지출 줄은 `60,000 → 내 몫 30,000`, 보조 줄 "정산 30,000". 카드 실적은 60,000 그대로. 원장은 두 줄이 모두 남는다. (Q3 정책과 같은 결과)

**예시 3. 컷오버 겹침**
컷오버 10/20 00:00. Actual에 10/19 카페 -4,500(현대카드)이 이미 있다. 폰은 이 결제 알림을 컷오버 전 시각(10/19 23:58)으로 늦게 보낸다.
컷오버 전 시각이라 새 항목을 만들지 않고 가져온 기록의 근거로만 붙는다. 4,500원은 한 번만 센다.
10/20 00:05에 같은 금액·같은 계좌 결제 알림이 오면, 10/20에는 가져온 기록이 없으므로(5.3절 첫 규칙은 같은 날 가져온 기록이 있을 때만 적용) 새 지출이다. 같은 날 같은 금액을 두 번 긁은 경우 가져온 기록이 둘이면 알림도 하나씩 짝지어 두 번 센다.

## 11. 결정과 구현 (2026-10-20)

### 승인

Hans(2026-10-20): "Q1-Q6 권장대로. 단, actual 에서 아직 처리되지 않은 거래(이름이 없거나 등)는 그대로 OnAll의 미처리 항목 표시 및 구현 용도로 쓰자. 그러니까, 실제로 그런 거래 알림이 들어왔고, 사용자가 아직 처리하지 않은 것인 상태를 반영하도록."

Q1–Q6은 위 표의 권장안이고, 덧붙인 말은 Actual에서 아직 처리하지 않은 거래를 자동으로 해결하지 말고 OnAll에서도 같은 미처리 상태로 보이게 하라는 뜻으로 구현했다(아래 "처리 안 된 행").

### 구성

| 무엇 | 어디 |

### 파일 `imported-history.json`

Actual의 `list_accounts`와 `list_transactions`가 돌려주는 필드를 그대로 담고 OnAll 정책은 적용하지 않는다. 정책은 앱(Swift)이 읽을 때 적용하므로 같은 파일을 몇 번이든 다시 읽어도 결과가 같다.

```json
{"version":1,"source":"actual","timeZone":"Asia/Seoul","through":"2026-10-19",
 "accounts":[{"name":"급여통장","kind":"bank","on_budget":true,"balance":1000000}],
 "transactions":[{"id":"…","date":"2026-10-19","account":"급여통장","amount":-4500,"payee":"가게","category":"식비","notes":null,"imported_payee":"가게 본점","transfer":"→ 티머니"}]}
```

`kind`는 `bank | prepaid | card`(Actual에는 없어서 도구에 넘긴다), `through`는 파일이 담은 마지막 날이다. 컷오버는 `through` 다음 날 00:00(파일의 시간대)이다.

### 폰까지 가는 길

1. 클라우드 스레드가 Actual 도구(읽기 전용)로 `list_accounts`, `list_transactions`(`since`=첫 날, `limit`=500, 500건을 넘으면 `until`을 당겨 여러 번)를 부르고 결과를 비공개 폴더에 파일로 저장한다.
2. `python3 tools/actual_import/make_history.py --accounts … --transactions … --through <오늘> --card "<카드 계좌>" --prepaid <선불 계좌> --out imported-history.json`. 계좌별로 행의 합이 Actual 잔액과 다르면(분할 부모가 같이 온 경우, 빠진 쪽) 종료 코드 1로 알려 준다. 이 파일을 git에 넣지 않는다(`.gitignore`에 있다).
3. Hans가 승인한 방식(Q5)대로 파일을 프로젝트 파일(비공개)에 두고 Hans가 내려받아 AirDrop → 파일 앱으로 폰에 옮긴다.
4. 앱 설정 → 지난 가계부 → 파일 고르기. 앱이 계좌·거래 건수와 정리할 거래 수, Actual 잔액과 다른 계좌를 보여 준다.
5. 가져온 뒤 프로젝트 파일과 폰의 원본을 지운다(앱은 `Application Support/Intake/imported-history.json`에 자기 사본을 보호 저장으로 가진다).
6. 라이브 전환 전에 한 번 더 같은 방식으로 가져오면 새 컷오버로 넘어간다(파일 전체를 바꾼다). 이미 등록된 계좌의 시작 잔액은 바뀌지 않는다.

### 변환 규칙 (구현)

모든 ID는 Actual 행 id에서 정해져 다시 가져와도 같다(`actual:<id>`). 시각은 날짜의 정오(KST)이고 "시각 미상"(정밀도 일 단위)이다. 같은 날 같은 종류·방향·금액이 여러 번 있으면(버스 요금 두 번, 두 계좌 사이를 같은 금액으로 오간 이체) 원장의 중복 판정이 같은 거래로 보지 않도록 6분씩 띄워 둔다(표시는 "시각 미상" 그대로).

| Actual | OnAll |
|---|---|
| `Starting Balances`, `잔액 조정` | 계좌 시작 잔액에 더한다(잔액 조정은 따로 합계를 남긴다). 카드에는 시작 부채가 없어 경고만 남기고 건너뛴다 |
| 음수, 이름 또는 분류 있음 | `expense`(카드는 부채 증가). 시각 미상 |
| 양수, 계좌 | `income`. 메모에 `원거래`가 있으면 정산(아래) |
| 이체 쌍(같은 날·같은 금액·`→ 상대`/`← 상대`) | `transfer` 한 건. 도착이 카드면 `cardPayment` |
| 파일에 없는 계좌와의 이체(닫힌 계좌) | 아래 "닫힌 계좌" |
| 짝 없는 이체, 카드에서 나가는 이체 | 검토 대기(`incompleteTransfer` / `unsupportedEvent`), 잔액에 넣지 않음 |
| 카드 계좌의 양수(환불) | 검토 대기(`missingOriginalEntry`). 금액만으로 원거래를 짝짓지 않는다 |
| 정산 입금 | `income` 한 건(메모의 `입금거래`로 묶은 모든 행의 합) + 원거래마다 받을 돈(`Obligation`, 상대는 "이름 없는 사람") + 그 입금이 갚은 `Settlement`. 보낸 사람 이름(`imported_payee`)은 읽지 않는다. 원거래가 파일에 없으면 정산하지 않고 일반 입금으로 두고 대기에 올린다 |

정산 연결(`ImportedSettlementSeed`)은 가계부 원장을 바꾸지 않는다. 앱은 실행할 때마다 이 연결을 `LifeState`의 시작값으로 넣는다(현재 라이브 모드의 `LifeState`는 저장되지 않기 때문이다).

### 닫힌 계좌

Actual 도구는 닫힌 계좌를 계좌 목록에서도 거래에서도 빼 버린다. 그런데 열려 있는 계좌에는 그 계좌와 주고받은 이체가 남아 있다(실제 내보내기에서 확인: 토스뱅크 등). 이 이체를 검토로 돌리면 잔액이 수백만 원씩 어긋나므로, 이체에 이름만 나오고 파일에 없는 계좌는 **자리표시 계좌**로 만든다. 시작 잔액은 닫힌 계좌가 0원으로 끝나도록(이체 합계의 반대) 정하고, 가져오기 경고(`counterpartNotExported`)에 이름을 남긴다. 이체는 한쪽 다리만 있는 `transfer`로 기록된다. Hans가 나중에 그 계좌를 실제로 쓰지 않으면 계좌 목록에서 숨기면 된다. (정책이라기보다 잔액을 맞추기 위한 처리이므로 메인 스레드에 알림.)

### 처리 안 된 행 (Hans의 추가 지시)

Actual에서 아직 처리하지 않은 행은 자동으로 해결하지 않고, 실제로 그 알림이 방금 와서 아직 처리하지 않은 것과 같은 상태로 둔다. 받은 알림 화면 맨 위 "가져온 기록 중 정리할 것"에 모인다(`IntakeLedger.pendingImports`).

| Actual의 상태 | OnAll의 상태 | 이유 표시 |
|---|---|---|
| 분류 없는 입금(이름 있음) | `income`으로 기록됨, 가계부 탭 "정리할 입금"에 뜸 | 무슨 입금인지 몰라요 |
| 분류 없는 결제(이름 있음) | `expense`로 기록됨 | 분류가 아직 없어요 |
| 분류는 있고 이름이 없는 결제 | `expense`로 기록됨 | 이름이 없어요 |
| 이름도 분류도 없는 출금 | 검토 대기(`unsupportedEvent`), 잔액에 넣지 않음 (실제로 설명되지 않은 출금 알림이 쌓이는 상태와 같다) | 다른 기록으로 설명되지 않은 출금이에요 |
| 짝 없는 이체 | 검토 대기(`incompleteTransfer`) | 이체 상대 기록이 없어요 |
| 카드 환불 | 검토 대기(`missingOriginalEntry`) | 어떤 결제의 환불인지 몰라요 |
| 예산 안↔밖 이체(Actual이 분류를 요구) | `transfer`로 기록됨 | 분류가 아직 없어요 |

기록되지 않은 행은 잔액이 Actual과 다르게 보이는 것이 맞으므로, 앱은 가져온 직후 계좌별로 "원장 잔액 − Actual 잔액 + 대기 중인 행"이 0인지 확인한다(`importReconciliation`). 0이 아닌 계좌는 가져오기 확인 창에 이름이 나온다.

### 설계와 다르게 한 것, 하지 않은 것

- **겹침 규칙을 하나로 줄였다.** 5.3절의 "같은 계좌·같은 금액·같은 날이면 근거로만 붙는다"는 컷오버가 `through` 다음 날 00:00이라서 가져온 행과 컷오버 뒤 알림이 같은 날에 놓일 수 없다. 그래서 규칙은 컷오버 시각 하나다: 그 전에 온 알림(알림 시각, 없으면 받은 시각)은 목록에 남기되 원장에 넣지 않고 "가져온 기록에 이미 있음"으로 표시한다. 9절 예시 3은 같은 결과다.
- **Actual의 분류(카테고리)·태그·메모는 아직 OnAll의 분류로 옮기지 않았다.** 분류를 OnAll에 두려면 거래의 배분(`TransactionAllocation`)이 필요한데, "활동 없음" 배분은 일정 시각 자동 묶기를 막는다(`TimeBinding`은 배분이 있는 거래를 건드리지 않는다). 가져온 지난 소비가 일정에 묶이지 않게 되는 부작용이라 정책으로 정해야 한다. 지금은 분류 없음 상태로 두고, 메모만 거래 이름이 없을 때의 이름으로 쓴다. (메인 스레드에 질문함)
- **받을 돈이 아직 안 들어온 정산**(Actual의 `list_settlements`)은 이 파일에 없다. 입금이 있는 정산만 연결한다.
- **내 몫을 보낸 `#정산` 지출**은 일반 지출로 둔다.
- 정산 입금이 여러 원거래를 갚으면 Actual이 쪼갠 행마다 받을 돈을 만든다. 하나라도 원거래가 파일에 없으면 그 입금은 정산하지 않는다.
- 카드의 시작 부채(`CreditInstrument`)는 아직 없다.
