# Account Discovery / Resolution

Pure domain logic in `Sources/NEOBudgetCore/Accounts`. No UI, no persistence, no correlator, no transfer pairing.
It was designed from an analysis of real notifications against final ledger records: only about 20% of
notifications could be tied to one account by app and instrument alone, so account identity is the main blocker
for automatic confirmation.

## Pieces

| Type | Role |
|---|---|
| `InstitutionCatalog` | Source (app name, provider hint, bundle id) → `InstitutionID`. Never from message text. Two apps of one bank (우리은행, 우리WON뱅킹) are one institution. |
| `AccountHintExtractor` | `RawNotification` → `AccountHints` (institution, instrument class, identifier). Separate from the transaction parser, whose contract is unchanged. |
| `AccountIdentifier` | Masked account number (`1002-123-456***`) or four-digit card tail. Only masked numbers with ≥ 6 visible digits are strong. Unmasked digit runs are never identifiers (dates, phones, amounts look the same). |
| `AccountRegistry` | `AccountProfile` (binding + display name + identifiers), `AccountCandidate`, `SourceRule`. Pure value type, `Codable`. |
| `RegistryAccountResolver` | Adapter to the existing `TransactionAccountResolver`. Anything but a safe resolution is `unresolved`. |

Display name and identity are separate: the binding (`AccountID` / `CreditInstrumentID`) is generated by the caller
(`makeID`), identifiers and rules point at the binding, and `rename` changes only the label.

## Decision (`AccountRegistry.resolve`)

1. Institution unknown → **ask** (`institutionUnknown`).
2. Strong identifier present (authoritative; never falls through to a rule):
   - matches exactly one active profile at that institution → **resolved**;
   - matches none → **new `AccountCandidate`** (recorded by `observe`, nothing bound);
   - matches several → **ask** (`identifierMatchesMultipleAccounts`); matches an inactive one → **ask**.
3. No usable identifier: a user `SourceRule` (institution + kind [+ app]) applies **only while its target is the only
   active profile of that institution and kind**. Otherwise **ask** (`sourceRuleHasSiblingAccounts`,
   `conflictingSourceRules`, `noIdentifier`, `weakIdentifier`).

## When the user must confirm

| Condition | Why | User action |
|---|---|---|
| New strong identifier | Could be a new account or a renumbered one | link to existing / confirm as new / dismiss |
| No identifier, no rule | Real data: card app with two accounts behind it; Toss with two bank accounts | create a source rule, or pick per transaction |
| Rule exists but a sibling account exists | The same message could be either | pick; rule stays a suggestion |
| Creating a rule while siblings exist | Guessing | must acknowledge explicitly |
| Identifier matches 2+ accounts | Overlapping masks | resolve the duplicate identifier |
| Matched account is inactive | Money into a closed account | reactivate or relink |
| Institution unknown | Cannot scope an identifier | add the alias or pick |

The registry refuses to bind one identifier (or compatible mask) to two accounts of the same institution.
Candidates keep only notification IDs as evidence, never text.
