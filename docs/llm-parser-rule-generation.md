# 처음 보는 알림의 파싱 규칙을 LLM으로 만들 수 있을까 (검토)

2026-11-06, 검토 문서만. 구현 없음. 폰 테스트에서 이름이 "거래"로만 나오거나 입금자 이름 자리에 앱 이름이 들어간 문제에서 나왔어요.

## 지금 상태
- `KoreanFinancialNotificationParser`는 키워드와 줄 모양으로 읽는 결정론 규칙이에요. 모르는 모양은 이름이 비거나(`merchantMissing`) 아예 읽지 못해요(`unreadable`).
- 앱은 읽지 못한 알림을 받은 알림 내역에 남기고, 이름을 못 읽은 거래는 상세 시트에서 원문을 보여주고 이름을 직접 받아요(2026-11-06 추가).

## 제안: "규칙 후보 생성기"
LLM이 거래를 직접 해석하는 게 아니라, 실패한 알림 몇 건을 보고 **선언형 규칙(JSON)** 을 제안하고 사람이 승인한 뒤에만 쓰는 구조예요.

1. 실패 알림을 모아요: 앱 이름, 제목, 부제, 본문. 이름·계좌번호·잔액은 기기에서 가려서(마스킹) 보내요. 테스터 수집(`20261025-테스터-알림-수집-방법.md`)과 같은 마스킹을 써요.
2. LLM(Haiku급)이 같은 모양끼리 묶고 규칙 후보를 만들어요. 출력은 정해진 스키마만 허용해요. 예: `{match: {app, contains[]}, kind, direction, amount: {after: "입금", unit: "원"}, name: {between: ["***", "잔액"]}}`.
3. 후보를 저장된 실제 알림 전부에 돌려서 맞는지 검사해요(금액이 본문 숫자와 일치, 기존 규칙 결과와 충돌 없음, 이미 맞게 읽던 알림은 그대로).
4. 통과한 후보만 "이 모양의 알림을 이렇게 읽을까요?" 카드로 사용자에게 보여주고, 승인하면 앱의 규칙 목록에 들어가요. 거절하면 버려요.

## 왜 규칙 JSON이고 직접 해석이 아닌가
- 금액·방향은 돈이라 매번 모델이 읽게 하면 틀렸을 때 장부가 바뀌어요. 규칙은 한 번 검증하면 같은 결과가 나와요.
- 오프라인·무서버 1차 출시와 맞아요. 규칙이 만들어진 뒤에는 기기 안에서 돌아요.
- 틀린 규칙은 승인 전에 걸러지고, 승인 뒤에도 규칙 단위로 끄거나 지울 수 있어요.

## 위험과 한계
- 개인정보: 알림에는 이름과 계좌가 있어요. 마스킹 없이는 보내지 않아요. 마스킹 때문에 이름 위치를 못 알아볼 수 있어서 "자리 표시"로 바꿔 보내요.
- 같은 모양이 최소 2~3건 있어야 규칙으로 일반화해요. 1건이면 원문을 보여주고 사용자가 직접 입력하는 쪽이 나아요.
- 규칙 스키마가 표현하지 못하는 모양(여러 금액, 외화)은 계속 실패로 남겨요.
- 비용은 실패 묶음당 1회 호출이라 작아요. 유료 기능(Haiku 클라우드, `20261102-Claude-API-카테고리-자동분류-검토.md`)과 같은 서버 경로를 쓸 수 있어요.

## 먼저 할 일(LLM 없이)
1. 규칙을 코드가 아니라 데이터(JSON)로 옮겨요. 지금 파서의 `classify`·`parseCounterparty`를 같은 스키마로 표현할 수 있어야 LLM 출력도 받을 수 있어요.
2. 실패 알림을 한곳에 모으는 화면(받은 알림 내역의 "읽지 못함" 필터)을 만들어요.
3. 사용자가 원문 위에서 "이 부분이 이름" 하고 고르면 규칙이 되는 수동 흐름을 먼저 만들어요. LLM은 이 흐름의 자동 제안 단계로 얹어요.

## 결론
가능하고, 위 순서(규칙 데이터화 → 실패 모음 → 수동 규칙 만들기 → LLM 제안)로 가면 안전해요. 1차 출시에는 수동 흐름까지, LLM 제안은 유료 기능과 함께 출시 이후를 권해요.
