# 개발 및 검증 환경

Core는 Swift Package이며 iOS SDK, Xcode, SwiftUI를 요구하지 않는다. 테스트 라이브러리는 Swift 도구에 포함된 Swift Testing을 사용한다. 런타임 외부 패키지는 없다.

## Windows

[공식 Swift Windows 설치 안내](https://www.swift.org/install/windows/)를 따른다. Swift뿐 아니라 Windows SDK와 C++ 빌드 도구가 필요하다. 기존 Visual Studio 설치가 있으면 필요한 구성 요소를 추가할 수 있으므로 먼저 설치 상태를 확인한다. 이 저장소는 도구를 자동 설치하지 않는다.

Swift 설치 후 새 PowerShell에서 확인:

```powershell
swift --version
git clone https://github.com/solhnsol/New_NEO_Budget_App.git
Set-Location New_NEO_Budget_App
# 작업 브랜치가 원격에 공개된 뒤 해당 브랜치를 선택한다.
swift build
swift test
```


2026-10-06 GitHub 인증 후 `main`, `plan/local-first-core`, `refactor/platform-neutral-boundaries` 업로드와 원격 커밋 일치 확인을 완료했다. Windows에서는 `refactor/platform-neutral-boundaries`를 clone해 이어서 작업한다. 명령은 `docs/handoff.md`를 참고한다.

2026-10-07 실제 Windows x86_64에서 Swift 6.4, Visual Studio Build Tools 2022 17.14, Windows 11 SDK 환경으로 `swift build`와 `swift test` 성공을 확인했다. ingestion 경계, red-team corpus, 합성 fixture, atomic promotion을 포함한 총 423개(Core 60 + Calendar 363)가 통과했다. Developer Mode 활성화 후 `.build/debug` 심볼릭 링크 경고도 더 이상 발생하지 않았다. 새 PowerShell이 설치 환경을 아직 반영하지 않은 경우 Visual Studio Developer Command Prompt를 로드하고 `SDKROOT`를 Swift의 `Windows.sdk` 경로로 지정해야 한다.

통과 기준: build 성공, 테스트 발견/실행, 실패 0개. Windows CI 도구/버전/공개는 별도 결정한다.

## 현재 에이전트 Linux 환경

Debian 13/aarch64. 시스템 Swift가 없어 공식 Swift 도구를 저장소의 `.tooling/`에 격리해 준비한다. `.tooling/`은 Git에서 제외되며 앱이나 Core의 배포 의존성이 아니다.

Package의 최소 manifest 버전은 Swift 6.0이다. 모든 지원 Swift 버전을 검증했다는 의미는 아니다. 실제 사용한 도구 버전과 테스트 결과를 기록한다.

검증 결과: Swift 6.4, Debian 13/aarch64에서 빌드 및 Swift Testing 12개 통과. Windows x86_64에서도 동일한 12개 테스트를 통과했다. Linux의 새 기본 Swift Build 실행은 격리된 libncurses 경로가 하위 링크 명령에 전달되지 않아 실패했고, 이 환경에서는 SwiftPM의 native build system으로 실제 실행을 완료했다. 이것은 Linux 도구 환경에 대한 우회이며 앱 소스 변경은 아니다.

이 Linux 환경에서 실행한 명령:

```bash
LD_LIBRARY_PATH="$PWD/.tooling/system-libs/usr/lib/aarch64-linux-gnu" \
SWIFTPM_MODULECACHE_OVERRIDE="$PWD/.tooling/module-cache" \
CLANG_MODULE_CACHE_PATH="$PWD/.tooling/clang-cache" \
.tooling/swift-6.4.0-RELEASE-debian13-aarch64/usr/bin/swift test \
  --build-system native --scratch-path .build/native \
  --cache-path .tooling/cache --config-path .tooling/config \
  --security-path .tooling/security
```

native 옵션은 사용한 도구에서 deprecated 안내가 있으므로 Windows에 이 우회를 그대로 강제하지 않는다. Windows의 정상 설치에서 기본 `swift test`를 먼저 확인한다.

### Day Timeline: browse / edit 모드

타임라인은 두 가지 모양을 가진다. 둘 다 같은 `TimelineEditor.geometry`에서 나오며, 변하는 것은 시간축(`TimelineAxis`)뿐이다.

| | browse (기본) | edit (길게 눌러 진입) |
|---|---|---|
| 목적 | 하루를 한눈에 | 15분 단위로 정확하게 |
| 시간축 | 일정 경계와 지출 시각 주변은 원래 크기, 긴 빈 시간과 아주 긴 일정의 가운데는 접음(접힘은 길이 라벨 없이 `⋮` 표시만) | **browse와 같다.** 편집 모드에 들어가도 시간축은 바뀌지 않는다. 핸들을 잡고 끌다가 멈추면 그 시각 주변(±90분, 15분 = 12pt)만 확대한다 |
| 리사이즈 핸들 | 없음 | 선택한 일정의 위·아래 핸들(●) |
| 전환 | — | 진입·종료 모두 **화면에서 아무것도 움직이지 않는다**(핸들만 나타나고 사라진다). "완료"나 빈 시간 탭으로 종료 |

연결된 거래는 별도 레일이 아니라 **해당 일정 블록 안**에 표시한다. 접힌(기본) 블록은 **금액이 큰 순으로 최대 2건**을 보이고, 나머지는 `+N건 · 합계 …`로 접는다(`InlineAllocationPlan`, `AllocationOrdering`). 높이가 모자라면 한 줄 요약 행("N건 · 합계"), 한 줄도 안 들어가면 제목 줄의 요약 칩으로 대체한다. 블록 높이는 시간만 반영하므로 거래가 많아도 커지지 않는다. 금액 순위에서 추정 금액은 그 값으로, 범위는 하한으로 세고 금액이 아예 없는 거래만 맨 뒤로 간다. 합계는 환불을 빼고 통화를 섞지 않으며 미확정이 있으면 그렇게 말한다(`LinkedTotal`). 일정에 속하지 않은 지출만 시간축의 독립 마커로 남는다(오른쪽 레일).

#### 핸들 드래그 중 확대 영역 이동 (`TimelineEditor.zoomAtFinger`)

- 편집 모드에서 시간축은 바뀌지 않으므로, 확대는 **핸들을 잡은 뒤** 손가락이 400ms 멈췄을 때(또는 잡은 채 움직이지 않았을 때) 한 번에 한 곳만 생긴다. 움직이는 손가락 아래에서는 시간축을 바꾸지 않는다.
- 확대 전후로 **선택된 시각은 바뀌지 않는다**. 그 시각의 화면 위치가 변하지 않도록 내용을 같은 양만큼 옮기고, 드래그 기준점(`fingerAnchorY`)도 새 시간축에 맞춰 다시 잡는다(좌표 연속성). 손가락과 핸들 사이의 간격도 유지된다.
- 시간축이 바뀌는 0.35초 동안의 손가락 값은 실제 드래그가 아니므로 무시한다.
- 확대는 **시작·종료 핸들만** 한다. 일정 이동이나 새 일정 만들기는 움직이는 동안 시간축이 바뀌면 안 되므로 멈춰도 확대하지 않는다. 이미 충분히 큰(편집 배율 이상) 곳에서는 아무 것도 하지 않는다.
- 4pt 이하의 떨림은 "멈춤"으로 본다. 손을 떼거나 취소하면 대기를 취소하고 확대 영역을 거두며, 확정 후에는 방금 움직인 가장자리가 제자리에 남는다.
- 확대 영역이 열릴 때 가벼운 햅틱(선택 틱)이 나온다.

#### 수정 중인 시각 표시

핸들을 끌거나 일정을 옮기거나 새 일정을 잡는 동안, 바뀌는 시각을 **왼쪽 시간축에** 그 가장자리 위치에 파란 배지로 보인다(리사이즈는 움직이는 쪽만, 이동·생성은 시작과 끝). 일정 블록 안의 시각은 손가락에 가려질 수 있기 때문이다. 배지와 17pt 안에 있는 시간 라벨과 접힘 표시(`⋮`)는 배지가 있는 동안만 숨겨서 겹쳐 보이지 않는다.

#### 시간축이 바뀔 때: 하나의 값으로 모든 것을 그린다 (`AxisTransition`)

시간축의 모양이 바뀌는 모든 경우(확대 영역 이동, 확대를 거둘 때, 열린 일정이 닫힐 때 등)는 하나의 `AxisTransition`(이전 모양, 새 모양, 기준 시각이 움직인 거리 `delta`)이 된다. 원인과 해법:

- **SwiftUI 애니메이션과 UIKit 스크롤 보정은 서로 다른 시계라 어긋난다.** 그래서 애니메이션을 쓰지 않는다. 진행도는 **시계로 계산한 하나의 숫자**(`AxisTransition.progress(at:)`, easeInOut 0.25초)이고, 매 프레임 `TimelineView`가 그 값으로 그린다. 이전 변화를 이어받아 겹치는(additive) 보간이 없어서 변화가 변화를 대체해도 값이 튀지 않는다.
- 일정 본체, 핸들, 시간 눈금, 접힘, 지출 마커, 미리보기가 모두 같은 `TimelineGeometry`(두 모양의 블렌드)에게 위치를 묻는다. 따로 움직일 수 없다. 눈금·접힘 표시는 한쪽 모양에만 있으면 페이드한다.
- **스크롤뷰는 변화가 끝날 때까지 제자리에 둔다.** 대신 내용을 `delta × 진행도`만큼 옮겨 기준 시각을 같은 자리에 붙잡고, 끝나는 순간 스크롤뷰를 `delta`만큼 한 번에 옮기면서 같은 갱신에서 내용 이동을 지운다. 두 값이 정확히 상쇄되어 화면은 변하지 않는다.
- 변화 중 내용 높이는 줄어들지 않는다(`TimelineGeometry.contentHeight`). 줄어들면 UIKit이 스크롤 위치를 강제로 줄여서(오프셋 clamp) 화면이 엉뚱한 양만큼 움직인다.
- 스크롤뷰가 따라갈 수 있는 범위(`ScrollProbe.shiftRange`)를 넘는 이동은 미리 그 범위로 줄인다. 그렇지 않으면 끝에서 한 번에 튄다. 짧은 하루에서는 편집 중 아래쪽 여유(320pt)가 필요하며, 확대 영역이 있거나 드래그 중일 때만 둔다.
- **확대를 반복해도 일정의 다른 쪽 가장자리는 화면에 남는다.** 확대 영역은 손가락을 붙잡으려고 내용을 밀기 때문에, 위아래로 반복하면 밀림이 쌓여 원래 일정이 화면 밖으로 나갔다. 이제 새 확대 영역을 열 때 일정의 다른 가장자리(끝 핸들을 끌면 시작)가 화면에 있으면 그대로 있도록, 그 가장자리를 향한 쪽 반경을 90분에서 75·60·…·0분(15분 단위)으로 줄인다(`TimelineEditor.radii`). 이미 화면 밖이면 건드리지 않는다.
- **놓을 때 드래그가 필요로 했던 스크롤을 전부 돌려준다**(`dragShift`). 확대가 열릴 때마다 손가락을 붙잡으려고 내용을 밀었는데, 놓고 나서 그만큼을 돌려주지 않으면 화면이 처음보다 위로 밀린 채 남는다(맨 위 일정을 늘렸다가 제자리로 놓으면 위쪽 영역이 잘려 있다가 한꺼번에 들어오던 문제). 이제 놓으면 핸들을 잡았을 때의 스크롤 위치로 부드럽게 돌아간다. 스크롤뷰가 그 위치를 가질 수 없으면(확대가 사라지며 여유 공간도 사라질 때) 끝에서 UIKit이 한 번에 clamp하지 않도록 변화를 계획할 때 이미 그 한계로 줄인다.
- 구조가 다른 `if/else`로 내용을 바꾸면 SwiftUI가 다른 뷰로 보고 격자·제스처 인식기·스크롤 위치를 통째로 다시 만든다. 그래서 변화 중에도 같은 뷰 구조를 유지한다. 새로 만들어진 제스처 호스트는 이전 스크롤 명령을 다시 실행하지 않는다.
- 측정: 데모 `-demo-preview script-zoom`이 24시간 일정에서 핸들 드래그(빠른 이동 → 멈춤 → 15분 조정 → 놓기 → 종료)를 실제 시간으로 재생한다. 화면을 녹화해 프레임마다 블록·핸들·눈금의 Y를 읽었다(편집 진입: 변화 없음, 확대: 손가락 아래 핸들이 모든 프레임에서 같은 Y, 놓기: 블록 가장자리가 단조롭게 이동하고 마지막 프레임에서 튀지 않음).

### 일정 탭: 제자리 확장

일정을 **탭하면 화면 전환 없이 그 블록이 펼쳐진다**(`ExpandedBlockView`). 한 번에 하나만 열리고, 다른 일정을 탭하면 기존 것은 접히고 새 것이 열린다. 같은 일정을 다시 탭하거나 빈 시간을 탭하면 접힌다.

- **보여 주는 것**: 제목, 시간, 캘린더, 그리고 Activity가 가진 유형·장소·참여자("나, 가영 외 2명")·태그. 이름은 읽기 모델의 `ActivityBadge.display`(`ActivityDisplay`)가 `LifeState`에서 풀어 주므로 UI는 조회하지 않는다. Activity에 아직 정보가 없으면 그렇게 말한다. 연결된 **거래 전체를 시간순**으로(다른 날 결제는 날짜로) 보이고 합계를 함께 보인다.
- **일정 내부 시간축**: 열린 일정의 시간 구간만 블록이 내용만큼 높아지도록 확대한다(`TimelineEditor.expansion`). 안쪽에 15분 눈금이 열린다. 일정의 위쪽은 그대로라 화면에서 블록의 윗변이 움직이지 않고, 열린 일정은 이웃 위로 전체 폭을 쓴다.
- **시간 조정과 분리**: 길게 누르기는 그대로 시간 이동/리사이즈(편집 모드)다. 두 모드는 서로 배타적이라 길게 누르면 확장이 닫히고 편집 모드로 들어가며, 편집 중에 탭하면 편집이 끝나고 그 일정이 열린다. 제스처나 결정이 진행 중일 때의 탭은 무시한다.
- 읽기만 한다. 제목·참여자 인라인 수정은 다음 단계, 복잡한 속성은 이후의 Inspector로 둔다. 새 화면과 큰 폼은 없다. 종일 일정과 지출 마커는 기존처럼 상세 시트를 쓴다.

편집은 제스처 중에는 캘린더에 쓰지 않고 로컬 미리보기만 갱신하며, 손을 뗄 때 `TimelineEditPolicy`로 확정한 범위를 `CalendarCommandService`에 **한 번** 보낸다.

| 동작 | 제스처 |
|---|---|
| 일정 열기 | 일정 탭(인라인 확장) |
| 편집 모드 진입 | **첫 번째** 길게 누르기. 핸들만 나타나고 시간·블록·스크롤은 그대로다(열려 있으면 닫힘) |
| 스크롤 | 편집 모드의 **일반 드래그**는 언제나 스크롤이다 |
| 이동 | 편집 모드에서 선택한 일정을 **다시** 길게 눌러 집어 올린 뒤 드래그(햅틱). 15분 단위, 길이 유지 |
| 시작/끝 조절 | 핸들(●)에서 시작하는 드래그 (최소 15분, 하단은 그날 끝까지). 핸들의 터치 영역은 44pt. 드래그는 터치가 **닿은 지점**에서 시작한다(pan은 손가락이 이미 움직인 뒤에 인식되므로 그 시점의 위치로 hit-test하면 빠른 드래그에서 핸들을 놓친다) |
| 빠른 이동 → 정밀 조정 | 핸들을 압축 구간(일정 가운데)으로 끌고 가면 몇 시간씩 빠르게 움직인다. 거기서 손가락을 **400ms** 멈추면 그 시각 중심으로 확대 영역(±90분, 12pt = 15분)이 옮겨 오고, 작은 움직임으로 15분 단위 조정을 한다. 다시 빠르게 끌면 다시 압축을 쓴다. 확대 영역은 하나만 있어 멈출 때마다 따라온다 |
| 편집 종료 | 일정 밖 탭(탭한 시각이 제자리에 남음) 또는 "완료" |
| 생성 | 빈 곳을 길게 누른 뒤 드래그 → 그 주변이 펼쳐져 15분 단위로 범위를 잡고, 제목·캘린더를 정해 저장 |
| 반복 일정 | 손을 뗀 시점에만 "이 일정만 / 전체 일정"을 묻는다. 날짜가 바뀌는 변경은 "이 일정만"만 가능. `thisAndFuture`는 노출하지 않는다 |

터치는 SwiftUI 제스처가 아니라 스크롤뷰에 붙인 UIKit 인식기(`EditGestureHost`)로 처리한다. 길게 누르기(0.3초)는 스크롤과 구분한다. 편집 모드의 pan은 **핸들에서 시작한 터치만 받고**(그 밖의 터치는 인식기가 아예 받지 않아 스크롤뷰가 기다리지 않는다) 나머지는 첫 이동부터 스크롤된다. 어떤 터치가 무엇을 뜻하는지는 순수 함수 `TimelineGestureRouter`가 정하고(표로 테스트), 좌표 변환(`TimelineAxis`)과 hit testing(`EditHit`)은 서로 독립이다. SwiftUI의 `LongPressGesture.sequenced(before: DragGesture)`나 자식 뷰의 `DragGesture`는 스크롤을 막아서 쓰지 않는다.

실패하면 미리보기를 되돌리고 이유를 알린다: 다른 곳에서 바뀐 일정(`conflict`, 최신 내용으로 새로 고침), 읽기 전용 일정/캘린더, 저장 실패(재시도 가능하면 "다시 시도"가 사용자가 닫을 때까지 남는다), 삭제된 일정, 접근 꺼짐. 충돌 감지는 타임라인을 그릴 때의 `revisionToken`(`EventBlock.revisionToken`)을 기대 revision으로 보낸다. 편집 중인 일정이 다른 곳에서 바뀌면 확대 영역이 따라가고, 사라지면 편집 모드가 조용히 끝난다.

겹치는 일정의 열 배치(`OverlapLayout`)는 읽기 모델의 값을 그대로 쓰며, 좌표로 바뀌는 곳은 `TimelineGeometry.blockFrame` 한 곳이다. 다른 배치로 바꿀 때는 그 함수만 교체한다.

데모 모드 전용 디버그 인자: `-demo-preview expand|edit|move|resize|create`(해당 상태로 멈춤), `-demo-preview script-zoom`(`-demo-long`과 함께: 핸들 드래그를 스스로 재생), `script-return`(첫 일정의 끝 핸들을 늘렸다가 제자리로 놓기), `script-oscillate`(위아래로 반복해 확대하며 유지), `-demo-fail-next-write`(첫 번째 쓰기를 실패시킴), `-demo-long`(오늘 30분·2시간·8시간 일정, 내일 24시간 일정으로 바꿈). 데모에는 읽기 전용 캘린더의 일정, 반복 일정, 한 일정에 연결된 거래 4건(`+N` 확인용)이 들어 있다.

## Day Timeline UI 재설계: 이틀 타임라인, 활동 통합, 거래 카드 (2026-10-09)

원칙: **캘린더 일정이 곧 활동이다.** 일정에 연결되지 않은 거래는 예외 상태가 아니라 정상이다. 도메인 모델(CalendarEvent/Activity)은 합치지 않았고, UI와 읽기 모델만 하나로 보이게 했다. 원장 의미는 바꾸지 않았다.

- **일정 = 활동 편집**: 펼친 일정의 `정보` 버튼이 `EventActivitySheet`를 연다. 유형·장소·참여자·연결된 거래를 한 시트에서 고친다. 모든 편집은 `ActivityTarget.event(key)` 명령이라 Activity는 처음 필요할 때 자동으로 만들어지고, 화면에 "활동 만들기/연결" 단계가 없다. 장소는 새 명령 `assignActivityArea`/`upsertArea`(Calendar 패키지)로 추가했다. `ActivityEditing`(순수)이 명령 생성과 "연결할 수 있는 거래"(어떤 활동에도 안 묶인 것, 일정 시각에 가까운 순) 목록을 만든다.
- **이틀 타임라인**: 연속한 두 날이 나란히 있고 시간 축(`TimelineAxis.browse(for: [날짜들])`)을 공유한다. 한쪽 날에 일정/거래가 있는 구간은 두 날 모두 펼쳐지고, 둘 다 조용한 구간만 접힌다. 세로 스크롤은 시간, 가로 스와이프는 하루씩 이동한다(`DaySwipe`: 거리 40% 또는 빠른 튕김이면 정확히 하루, 손가락을 따라가되 최대 한 칸). 가로 우세한 드래그만 스와이프로 인정하고 나머지는 스크롤이다(`EditGestureHost.swipePan`, 편집 중에는 꺼짐). 모델은 [어제, 첫날, 둘째 날, 다음 날] 4일을 읽어 두어 스와이프가 끝나는 프레임에 바로 다음 날이 보인다. 날이 바뀌어 축 모양이 달라지면 화면 맨 위 시각을 고정점으로 한 시계 구동 전환(`timelinesDidChange`)을 쓴다. 두 번째 열에서도 길게 누르기·핸들 드래그·새 일정 만들기가 같은 편집기로 동작한다(`Preview.column`).
- **거래 카드**: 별도 레일을 없애고 일정과 같은 열에 거래를 시각 위치의 독립 카드(`TransactionCardView`)로 그린다. 일정 시간 중의 미연결 거래도 그 일정의 일부로 세지 않는다(시각만으로 귀속하지 않는다). 연결된 거래는 일정 블록 안에, 일정 시간 밖에 결제됐지만 연결된 거래는 일정 안에 자기 시각으로 남는다. 합계는 기존 `DaySummary` 그대로여서 이중 집계가 없다.
- **겹치는 일정**: 좁은 세로 열로 쪼개지 않는다(`DayContentLayout`). 모든 카드가 열 전체 폭을 쓰고, 겹치는 카드는 왼쪽에서 한 단계씩 들여 쌓는다. 완전히 포함된 일정은 좌우로 모두 들여 안쪽 카드로 보인다. 카드의 위·아래 경계는 항상 실제 시각이다. 제목은 모든 카드 위의 별도 층에 그려, 겹쳐도 가려지지 않는다: 먼저 아래로(자기 카드 안에서), 그래도 안 되면 같은 줄 오른쪽으로, 마지막으로 다음 빈 줄로 옮긴다. 선택/펼친 카드는 맨 위로 오고 실제 경계에 핸들이 붙는다. 3개 이상 겹침에서도 각 카드에 닿을 수 있는 노출 영역이 있고(테스트로 검증), 폭은 열의 절반 이상 유지한다.
- **데모**: `-demo-overlap`(포함·부분 겹침·동시 시작 5개·미연결 거래).
- **검증**: 앱 테스트 131개(빈 날/바쁜 날, 포함·부분·3개 이상 겹침, 좁은 열에서 5개 동시 시작 제목, 미연결/연결/일정 밖 시각 거래, 두 번째 열 편집, 스와이프 규칙, 공유 축, 전환 앵커) + 패키지 408개 통과. 시뮬레이터(iPhone 18 Pro, 17e)에서 가로 스와이프·세로 스크롤·첫/둘째 열 길게 누르기와 핸들 드래그를 직접 확인했다.

- **날짜 이동 시 튐 수정**: 녹화 영상에서 두 가지를 확인했다. (1) 시간 축을 보이는 이틀에만 맞춰서, 날을 넘길 때마다 접힘/펼침이 달라져 일정이 한꺼번에 ~100px 밀렸다 돌아왔다. 이제 축은 보이는 이틀과 이웃 이틀(스트립 4일)에 맞추고, 이웃이 합류/이탈해도 이벤트 가장자리가 실제로 바뀔 때만 모양이 바뀐다(`timelinesDidChange(_:axisDays:)`). (2) 종일 일정 유무로 날짜 헤더 높이가 달라져 그리드 전체가 위아래로 움직였다. 헤더는 이제 항상 같은 높이(날짜 줄 + 종일 한 줄, 더 있으면 `+N` 메뉴)다.

### 이틀 시간축 정책: 메인 날짜 중심의 비대칭 공유 압축 (2026-10-09, 위의 "스트립 4일에 맞춘 축"을 대체)

- **Main/Secondary**: 선택된 날짜(왼쪽)가 Main, 오른쪽이 Secondary다. 표시 우선순위일 뿐 일정의 중요도 판단이 아니고, 두 날짜는 **같은 시간→Y 좌표계 하나**를 쓴다(`TimelineAxis.browse(main:secondary:)`). 날짜별로 다른 세로 좌표계는 없다.
- **압축**: 기본 압축은 Main의 일정·거래로만 정한다(혼자 있을 때와 똑같이 접는다). Secondary는 최소 가독성만 보탠다: Main이 접은 구간에 Secondary의 일정/거래가 있으면 그 항목이 최소 높이(24pt)로 그려질 만큼만 그 구간을 연다(`TimelineAxis.assisted(by:)`, 배율은 browse 배율을 넘지 않는다). 구간 높이 = max(Main이 요구한 높이, Secondary의 최소 필요 높이). 그래서 Secondary 일정이 많아도, 예전의 "둘 중 어느 쪽이든 닿으면 전부 펼침" 규칙보다 축이 덜 늘어난다(테스트). Main이 이미 충분한 크기로 보여 주는 시간에는 아무것도 더하지 않는다. 짧게 남는 접힘 조각(<60분)은 합쳐서 접힘 표시가 쪼개지지 않게 한다.
- **날짜 전환**: 스와이프가 확정돼 새 Main이 정해진 뒤에만 축을 다시 계산한다(스와이프 도중에는 축이 변하지 않아 가로 이동과 재계산이 부딪치지 않는다). 기존 축에서 새 축으로의 전환은 기존 시계 구동 보간(`AxisTransition`)을 쓰고, **화면 중앙의 시각**을 고정점으로 스크롤을 보정한다.
- **편집**: 편집이 시작되면 그 순간의 기본 압축 축을 고정한다(`frozenBrowse`). 편집 중 일정이 이동·변경돼도, 날짜 데이터가 다시 읽혀도 축은 모양을 바꾸지 않는다. 편집을 끝내면 축이 새 날짜 상태를 따라 부드럽게 바뀐다. 길게 누르기·dwell 확대·15분 스냅·실패 롤백은 그대로다.
- **접근성**: Secondary의 일정과 거래도 Main과 같은 규칙으로 그려지고 탭·길게 누르기·편집이 된다(테스트: 두 번째 열 편집).

## 개발 중 빠른 검증 (2026-10-09 측정)

`tools/dev/check.sh`가 단계별 소요 시간을 출력하고, 오류와 테스트 요약만 보여 주며, 전체 로그는 `$TMPDIR/onall-check-logs`에 남긴다. 파생 데이터 폴더와 시뮬레이터는 하나만 재사용하고 아무것도 지우지 않는다. `CHECK_TIMEOUT`(초, 기본 600)을 넘기면 감시 프로세스가 실행을 끊는다.

| 목적 | 명령 | 측정 시간(이 Mac, 웜) |
| --- | --- | --- |
| 타입 확인만 | `tools/dev/check.sh build` | 2~5초 |
| 패키지(도메인) 수정 | `tools/dev/check.sh pkg MeaningCommandTests` | 2초 (전체 498개: 1초) |
| 앱 UI/레이아웃 수정 | `tools/dev/check.sh app --file DayContentLayoutTests` | 5초 |
| 특정 테스트만 | `tools/dev/check.sh app 'someTest()'` | 5초 |
| 앱 전체 테스트 | `tools/dev/check.sh app` | 4~5초 |
| 화면 확인(빌드+설치+실행+스크린샷) | `tools/dev/check.sh ui -demo -demo-overlap` | 4초 |
| 병합 전 전체 회귀 | `tools/dev/check.sh full` | 6초 |

측정한 병목(시간을 재서 확인한 것):

- **빌드**: 파일 하나를 고친 증분 빌드는 2~5초(`TimelineAxis`, `TimelineGridView`, 테스트 파일, 패키지 소스 모두 비슷). 클린 빌드는 앱 36초, 패키지 `swift test` 40초, iOS 패키지 스킴 20초. 클린 빌드를 불필요하게 반복하는 것이 가장 큰 낭비다.
- **테스트 실행**: 앱 137개가 0.2초, 패키지 498개가 0.05초. 러너 시작과 시뮬레이터 연결이 4~16초(첫 실행이 느림). 테스트 자체는 병목이 아니다.
- **시뮬레이터**: `simctl` install 0.2초, launch 0.1초, screenshot 0.5초. 종료 후 다시 부팅하면 8초.
- 따라서 이 환경에서 한 번의 전체 검증은 웜 6초, 완전 클린이어도 약 2분이다. 20분이 걸렸다면 빌드/테스트가 아니라 다음 같은 낭비였다: 클린 또는 전체 재빌드를 되풀이함, 시뮬레이터 두 대가 동시에 켜져 있어 `simctl booted`가 엉뚱한 기기를 가리킴, 출력을 `sort`/`head`로 끝까지 모았다가 보느라 멈춘 것처럼 보임, 녹화·스크린샷을 타이밍 없이 반복함. 한 번 600초를 넘긴 `xcodebuild test`의 원인은 재현하지 못했다(같은 명령이 이후 3초에 끝남). 그래서 감시 타임아웃과 로그 파일을 넣었다.

운용 규칙:

1. 수정마다 해당 모듈의 관련 테스트만(`pkg <필터>` 또는 `app --file`), UI는 `ui`로 화면까지 본다.
2. 전체 회귀(`full`)는 기능을 마칠 때와 병합 전에 돌린다. EventKit 계약 테스트(`Platform/iOS/EventKitContractHost/run-contract.sh`)는 EventKit 어댑터를 건드렸을 때와 병합 전에 따로 돌린다.
3. 테스트를 줄이거나 단언을 약하게 하지 않는다. 범위를 좁히는 것은 실행 선택일 뿐이고, 건너뛴 테스트는 보고서에 적는다.
4. `xcodebuild`는 `-derivedDataPath`를 고정하고, 시뮬레이터는 `SIM`(기본 iPhone 18 Pro) 하나만 켠다. 다른 기기가 켜져 있으면 `simctl shutdown`으로 끈다.
5. 긴 명령은 로그 파일로 보내고(`> log 2>&1`) 필요한 줄만 읽는다. 파이프 끝의 `sort`/`head`는 프로세스가 끝나야 출력을 낸다.

## Adaptive Space Allocation 엔진 (순수 계산, 2026-10-09)

`Platform/iOS/OnAllApp/OnAllApp/Timeline/Allocation/`: `AdaptiveLayoutModels.swift`(입출력), `AdaptiveLayoutEngine.swift`(계산), `AdaptiveLayoutAdapter.swift`(`DayTimeline` → 입력). SwiftUI·제스처·기존 렌더링 코드는 건드리지 않았고 아직 아무 화면도 이 엔진을 쓰지 않는다.

- **입력**(`AllocationInput`): Main/Secondary 날(일정, 연결된 거래, 미연결 거래), viewport 높이, 콘텐츠 열 너비, Dynamic Type 배율(`textScale`), 표시 모드(`browse`/`editing(frozen:)`), 이전 레이아웃의 상태(`previous`), 크기 파라미터. 스크롤 위치는 입력이 아니다(테스트로 확인). 그래서 스크롤만으로는 재계산할 이유가 없고, 콘텐츠·크기·글자 크기·모드가 바뀔 때만 한 번 계산한다.
- **출력**(`AdaptiveLayout`): 두 날이 공유하는 `TimelineAxis`(기존 구조 재사용), 일정별 표시 수준(`title`/`preview`/`full`)과 최소·선호·확장 높이, 겹침 표현, 거래 묶음(`cluster`/`rows`), 콘텐츠 높이, 스크롤 필요 여부와 부족한 높이, 다음 계산에 넘길 상태.
- **공간 배분 순서**: ① 최소 표현(모든 일정은 제목, 밀집 거래는 묶음)을 먼저 보장 → ② 남으면 Main의 일정 상세(linked 거래 행)와 묶음 해제 → ③ Main이 쓸 수 있는 것을 다 쓴 뒤에만 Secondary를 확장. 최소 표현도 못 들어가면 그때만 스크롤(`requiresScroll`)이고, 부족한 높이는 `scrollableHeight`로 정확히 나온다. 공간이 모자라면 우선순위의 뒤쪽(Secondary, 상세 → 요약)부터 되돌린다.
- **시간축**: 항목마다 "이 시간 구간은 이 높이 이상"이라는 요구(배율)를 만들고, 각 분은 요구 중 가장 큰 배율을 따른다. 요구가 없는 조용한 구간은 접고, 긴 일정(120분 초과)은 양 끝을 읽을 수 있게 두고 가운데를 압축한다. Main 항목 주변은 browse 크기로 남긴다. Secondary 항목은 최소 높이만 요구한다. 연결된 거래는 일정 안에 그려지므로 자기 시각을 요구하지 않는다.
- **일정 겹침**: 열을 쪼개지 않는다. 포함 관계(`contained`, 왼쪽 한 단계 + 오른쪽 안쪽)와 부분 겹침(`partial`, 왼쪽 한 단계)만 있고, 들여쓰기는 최대 1단계다. 3개 이상 겹치면 `summarisesTitles`로 제목 중심 요약을 표시하게 한다.
- **거래**: 미연결 거래는 일정 시간 안에 있어도 독립된 줄이다. 시간 간격 20분 이하의 연쇄가 3건 이상이면 묶음(같은 날, 미귀속 거래만)이고, 여유가 생기면 한 줄씩으로 풀린다. 묶음에도 모든 거래 id가 남아 접근 경로가 보존된다. 합계는 (종류: 소비/수입/환불/이체, 통화)별로만 더하며 섞지 않고, 금액이 미정인 거래는 합계 대신 `unknownCount`로 센다.
- **안정성**: 같은 입력이면 같은 출력(입력 순서와 무관). `previous`를 넘기면 단계를 올릴 때 여유 높이(16pt)를 요구해서, 데이터가 조금 바뀌어도 많은 항목의 단계가 뒤집히지 않는다. 편집 중(`editing(frozen:)`)에는 받은 레이아웃을 그대로 돌려준다.
- **미구현**: 엔진 결과를 SwiftUI 렌더링과 연결하는 일, 거래 묶음 카드 UI, 제목 요약 UI, 들여쓰기 그리기, Main 전환 시 이전 레이아웃과의 보간, 결과 캐시. 기존 `DayContentLayout`/`TimelineAxis.browse(main:secondary:)`는 그대로 쓰이는 중이다.
- **테스트**(`AdaptiveLayoutEngineTests`, 26개): 양일 한가/메인만/보조만 바쁨, 둘 다 많음, 겹침(부분·포함·3개 이상), 묶음과 해제, 일정 안의 미연결 거래, 일정 밖 시각의 연결 거래, 소비·수입·환불·이체·통화 혼합 합계, 아주 작은 viewport와 Dynamic Type, 결정성(입력 순서 무관), 데이터 변동 안정성, 긴 일정 중앙 압축, 예산 초과 시 스크롤.

개발 검증 메모(위 표에 이어서): 테스트가 실패하면 `xcodebuild test-without-building`이 결과를 낸 뒤에도 끝나지 않는 일이 두 번 있었다(원인 미확인, 통과하는 실행에서는 없음). 그래서 `check.sh`의 감시 타임아웃 기본값을 240초로 줄였다. 실패했다면 로그의 `✘` 줄을 먼저 보고, 오래 걸리면 `CHECK_TIMEOUT=120`으로 다시 돌린다.

### Adaptive Space Allocation 정책 보완 (같은 브랜치, 위 설명 중 거래 묶음 부분을 대체)

여전히 순수 계산과 테스트뿐이다. SwiftUI·제스처·화면 전환, EventKit, 금융 원장 로직은 건드리지 않았다.

- **거래 시각과 활동 귀속은 독립**: 일정 시간 안에서 발생한 연결 거래는 그 일정 안의 줄(`insideRange`)이고, 시간 밖에서 발생한 연결 거래는 실제 발생 시각에 독립 줄(`TransactionLine`)로 간다. 줄에는 `LinkMetadata(eventID, happenedOutsideEventRange)`가 붙어 색·보조 라벨·점선 같은 표현을 UI가 고를 수 있다(줄 자체는 보통 거래와 같은 대비). 일정에서 시작 시각과 거래 시각은 바뀌지 않는다. 일정 Focus 상세에는 시간 밖 연결 거래도 원래 시각·연결 관계(`relation`)와 함께 나온다. 일정 시간 안이어도 연결되지 않은 거래는 독립 줄이다.
- **중복 집계 없음**: 같은 거래를 여러 곳(일정 안, 줄, 다른 일정, Focus)이 참조해도 `ledgerTotals`는 거래 id당 한 번만 센다.
- **고정 묶음 기준 제거**: "20분·3건" 규칙을 없앴다. 거래는 기본적으로 개별 줄이다. 두 줄이 서로 닿을 때만(보통 시간 배율로도 간격을 못 만드는 경우, `Δ분 × browse 배율 < 줄 간격`) 합칠 수 있는 후보가 되고, 실제로 합치는 것은 높이가 부족할 때뿐이다. 2건도 부족하면 합쳐지고, 10건도 공간이 있으면 모두 줄로 남는다(줄 사이 간격이 시간축 요구로 확보된다). 멀리 떨어진 거래는 압축 때문에 가까워졌다는 이유로 합쳐지지 않는다(합칠 수 없는 쌍이고, 모자라면 스크롤). 합칠 때는 간격이 가장 좁은 쌍부터, 보조 날부터 합치고, 여유가 생기면 반대 순서로 푼다.
- **Overflow**: 의미 있는 그룹이 아니라 공간 부족의 시각적 표현이다(`TransactionOverflow`). 원본 거래 id·시각·종류·금액을 `members`에 모두 보존하고, 기본 요약은 종류별 건수(`countsByKind`)다. 종류·통화별 합계(`amountTotals`)는 있지만 한 종류·한 통화일 때만 `showsAmountTotal`로 합계를 내세울 수 있다.
- **일정 외부 헤더**: 일정 카드의 제목이 독립 거래 줄과 같은 자리를 쓰려 하면(제목 너비와 줄 너비가 열 너비를 넘고 줄이 제목 줄에 걸칠 때) 순서대로 시도한다. ① 시작 경계 위쪽에 아무것도 없을 때 외부 헤더(`EventHeader`, 일정과 같은 eventID, 시간 범위에 포함되지 않음). ② 헤더 자리가 없으면 제목 축약(`abbreviated(maxWidth)`). ③ 축약할 폭도 없으면 그 구간 확대(`expandedRange`, 축만 바뀌고 시간은 안 바뀜). 단, 확대로 화면 높이를 넘으면 하지 않는다. ④ 그래도 안 되면 `cramped`(제목을 자르되 거래 줄 위에 겹쳐 그리지 않음). 헤더 자리는 다른 일정 카드·거래 줄·다른 헤더와 닿으면 쓰지 않으므로, 겹친 일정이 부모 카드 위에 헤더를 얹는 일도 없다. 날짜 열은 서로 다른 열이라 헤더는 자기 열 안에서만 판단한다.
- **터치 영역**: `TouchTarget`이 눈에 보이는 높이(`visual*`)와 실제 터치 높이(`touch*`, 최소 44pt)를 분리한다. 터치 영역이 서로 닿는 일정·거래는 `TouchConflict.candidates`(선택 후보)로 돌려준다. 일부러 겹치는 일정끼리, 일정 위의 거래 줄은 충돌로 보지 않는다.
- **Focus 계약**: `FocusTarget`(`event(eventID)` / `overflow(overflowID, transactionIDs)`)을 일정과 Overflow가 같이 쓴다. `AllocationInput.focus`를 주면 대상의 날짜가 Main이 되고 다른 날은 `SecondaryPresentation.headerOnly(height)`로 줄어든다. 타임라인은 늘리지 않고 그 날 하나로 작은 맥락 영역(`focusContext`)에만 쓰며, 상세는 `FocusLayout`이 필요한 높이·가용 높이·내부 스크롤 필요 여부(`detailNeedsInternalScroll`, `detailScrollableHeight`)와 행(`rows`)으로 계산한다. 종료에 필요한 `FocusRestore`(원래 Main/Secondary 날짜, 기준 시각, 이전 레이아웃 상태)를 입력으로 받아 그대로 돌려준다. 없는 대상이면 일반 레이아웃으로 돌아간다. 전환 UI와 애니메이션은 구현하지 않았다.
- **유지한 것**: 16pt 히스테리시스, 메인 우선·최소 정보 보존·보조 확장 순서, 모든 정보를 보여 준 뒤 남는 높이를 채우지 않는 것(테스트), 스크롤 위치가 입력이 아닌 것, 결정성, 겹치는 일정의 id 보존과 최대 한 단계 들여쓰기.
- **테스트**: `AdaptiveLayoutEngineTests` 46개(26 → 46). 묶음 규칙이 없어지면서 그 규칙을 검증하던 5개(밀집 묶음, 먼/적은 거래 비묶음, 날짜 간 묶음, 혼합 합계, "일정 시각 밖 연결 거래는 일정에 속하고 줄이 없다")는 새 정책의 Overflow·연결 거래 테스트로 바꿨다. 그 외 기존 단언은 필드 이름만 바꿨을 뿐 그대로다. 전체: 앱 183개, 패키지 498개 통과.

### AdaptiveLayoutEngine의 Browse Mode 통합과 검증 (feat/adaptive-timeline-browse-integration)

Focus Mode는 구현하지 않았다. EventKit 어댑터와 금융 원장 의미론은 바꾸지 않았다.

- **연결**: `TimelineEditor`가 그리드가 알려 주는 환경(`AdaptiveEnvironment`: 화면 높이·열 너비·글자 배율·Dynamic Type 이름)과 두 날의 `DayTimeline`으로 엔진을 돌리고(`adaptive`), 공유 시간축은 그 결과의 축이다. 환경이 한 번도 보고되지 않았으면 기존 `TimelineAxis.browse(main:secondary:)`를 쓴다(기존 편집기 테스트가 그대로 통과). 결과는 (두 날, 환경)이 같으면 재사용한다. 스크롤 위치는 환경에 없고, 제목 너비는 실제 폰트(`TextMeasurer`, `UIFontMetrics`)로 엔진이 돌 때 한 번 재서 `AllocationInput.titleWidths`로 넘긴다. 그리는 동안에는 저장된 값을 찾기만 한다. 편집 중에는 레이아웃을 고정하고, 끝나면 바뀐 것을 한 번에 반영한다. 날짜가 바뀌어 축이 달라지면 화면 중앙 시각을 고정점으로 한 기존 시계 구동 전환을 쓴다.
- **그리기**: `DayRenderPlan`(순수)이 엔진 결과를 사각형으로 만든다. 그리기와 터치 판정이 같은 계획을 쓴다. 일정 카드에는 시간을 다시 쓰지 않고(시간축이 말해 준다), 엔진이 정한 만큼의 내부 거래 행만 둔다. 외부 헤더는 같은 eventID, 옅은 배경·밑줄, 카드 위쪽 굵은 시작선. 거래는 한 줄(연결 거래는 링크 표시·점선·"연결: 일정" 라벨, 금액과 이름은 항상 정상 대비), Overflow는 캡슐 요약 카드(건수 중심, 폭이 모자라면 건수만). 겹침은 한 단계 들여쓰기이고, 제목이 서로 밀려난 일정(3개 이상)은 한 줄 요약 메뉴로 각각 고를 수 있다. 터치는 하나의 탭 처리기가 계획으로 판정하며, 터치 영역이 닿거나 줄이 짧은 일정을 완전히 덮으면 선택 대화상자가 후보를 보여 준다. Overflow 탭은 임시 목록 시트(`FocusTarget`으로 이어질 안정적인 id 포함)를 연다.
- **발견·수정한 결함**: ① 겹침 묶음이 포함 관계로 사슬처럼 이어져 하루의 모든 일정 제목이 요약으로 숨던 문제 → 제목이 실제로 밀려난 일정과 그 이웃만 요약. ② Overflow 요약 숫자가 잘리던 문제 → 전체가 안 들어가면 건수만. ③ 큰 글자에서 요약 바가 화면을 차지하고 시간 라벨이 줄바꿈되던 문제 → 요약 바 글자 크기 상한과 한 줄 고정. ④ Overflow 카드가 자기 폭을 넘어 번지던 문제 → 잘라서 그림.
- **알려진 동작**: 날짜를 왕복하면 화면 중앙 시각 유지 때문에 세로 위치가 조금(관찰 ≈25pt) 어긋날 수 있다. 일정이 적은 날에서는 내용이 짧아 스크롤이 0에서 막혀 보정이 한쪽만 적용되기 때문이다(전환 자체는 이어서 움직이며 점프하지 않는다). 전환 도중(약 0.24초)에 들어오는 스와이프는 무시된다.
- **테스트**: 새로 `DayRenderPlanTests`(16), `AdaptiveCacheTests`(6). 앱 205개, 패키지 498개 통과. 데모 `-demo-dense`(짧은 일정 연속, 긴 제목 + 거래, 거래 5건 연속, 바쁜 보조 날).

### 상단 주간 막대 (시스템 캘린더 형태)

참고 영상(60fps)을 프레임 단위로 보고 맞췄다.

- **모양**: 보이는 두 날이 하나의 캡슐에 들어간다. 캡슐은 채운 원의 중심에서 시작해서 왼쪽 둥근 끝은 원 밑에 가려지고 오른쪽만 보인다. 원은 평소 검정(다크 모드에서는 흰색), 그 날이 오늘이면 포인트 컬러이고, 둘째 날 숫자는 캡슐 안의 회색이다. 주의 끝에서는 캡슐이 막대 가장자리에서 둥글게 멈춘다.
- **움직임**: 손가락을 따라가지 않는다. 타임라인을 스와이프하다가 놓으면 그 날로 가게 되는 지점(`DaySwipe`의 거리 기준)을 넘는 순간 `pendingShift`가 바뀌고, 그때 햅틱이 울린다. 원은 옛 날짜에서 사라지고(페이드), 새 날짜에서는 그 날짜 칸의 중심에서 커지며 나타난다(왼쪽에서 오른쪽으로 미끄러지지 않는다). 캡슐은 그다음에 액체처럼 움직인다: 왼쪽 끝(원 밑)은 빠르게 따라가고 오른쪽 끝은 스프링으로 조금 늦게 따라온다. 손가락이 기준 안으로 돌아오면 같은 방식으로 되돌아가고, 빠른 튕김은 거리 기준에 닿기 전에도 결정한다. 날짜가 확정될 때는 선택 날짜가 하루 이동하는 만큼 `pendingShift`가 0으로 돌아가 같은 업데이트에서 애니메이션 없이 정리되어 원과 캡슐이 제자리에 있다. 날짜를 탭으로 골라도 같은 모션이다.
- **날짜를 직접 눌러 이동할 때**(주간 막대, 오늘 버튼, 화살표): 참고 영상처럼 막대는 누르는 즉시 바뀌고(`pendingShift`에 이동 일수를 넣는다), 하루 차이는 스와이프가 놓였을 때와 같은 가로 슬라이드(0.22초)로 타임라인이 옮겨 가며, 이틀 이상 떨어진 날은 중간 날들을 훑지 않고 빠른 크로스페이드(0.12초 사라짐 → 날짜 교체와 읽기 → 0.2초 나타남)로 바뀐다. 구현은 `DayTimelineScreen.goTo(_:)`.

### 주 스트립: 연속 스트립, 주 단위 페이징, 먼 날짜 슬라이드

- 주 스트립은 선택 주 기준 앞뒤 2주(42일)를 한 줄로 두고, 모든 날짜와 캡슐을 `InterpolatedView`(Animatable)가 주는 하나의 보간값(`viewOffset`)으로 배치한다. 날짜마다 따로 애니메이션하지 않으므로 페이지가 넘어가는 중에 숫자가 겹치지 않는다.
- 스와이프/탭이 다른 주의 날을 가리키면 `viewOffset`이 그 주 시작으로 옮겨가며 스트립이 함께 슬라이드한다. 캡슐은 길이를 유지한 채 보이지 않는 다음 주 날짜로 이어진다(주 끝에서 줄어들지 않음).
- 스트립 자체는 손가락을 따라 드래그되어 옆 주가 보이고, 30% 이상 끌거나 빠르게 넘기면 같은 요일을 유지한 채 한 주 이동한다(`onPage`). 아니면 제자리로 돌아온다.
- 떠나는 공은 자기 날짜를 따라 슬라이드하며 페이드아웃한다(`ghosts`, 날짜 번호 기준 배치).
- 이틀 이상 떨어진 날을 탭하면 사이의 날들을 읽어(18일 이내, 그 이상이면 양 끝 근처만) 타임라인 옆에 실제로 붙여 두고 빠르게 지나간다(`readDays`/`adopt`, 페이드 없음). 탭 이동에도 햅틱(`Haptics.snap`)이 있다.
- 검증: 시뮬레이터 녹화로 주 경계(토→일) 스와이프와 스트립 페이징을 확인. 햅틱, 오늘(강조색) 전환 프레임, Apple 타이밍과의 일치도는 확인하지 못했다.

### 일정 카드 모서리의 시작/종료 시각

- 카드 오른쪽 위에 시작 시각, 오른쪽 아래에 종료 시각을 24시간제(`H:mm`)로 작게 표시한다(`CornerTime`, `Formatting.shortClock`).
- 전날에서 이어지는 일정은 시작을, 다음 날로 이어지는 일정은 종료를 표시하지 않는다(실제 시작/끝이 아니므로).
- 제목이 옆/아래로 밀린 카드는 시작 시각을 생략하고, 종료 시각은 카드에 남는 높이가 부족하거나 거래 줄/묶음 카드가 그 자리를 덮으면 생략한다.
- 시뮬레이터 스크린샷으로 데모 데이터에서 확인했다. 큰 글자 크기와 헤더가 붙은 카드의 모습은 따로 보지 않았다.

### 거래 표시: 일정은 카드, 거래는 텍스트

- 일정 안(연결 + 일정 시간 안)의 거래는 카드 안의 일반 텍스트다. 상호명은 일정 제목과 같은 X에서 시작하고 금액은 시작 시각과 같은 오른쪽 끝에 맞춘다(아이콘·별도 들여쓰기 없음). 공간이 없으면 제목 줄 오른쪽에 "거래 N건 · 합계"를 글로 쓰고(칩 없음), 행이 일부만 보이면 "그 외 N건".
- 일정 밖 / 연결 안 된 거래는 독립 행이다: 날짜 열 왼쪽 가장자리의 작은 점에서 일정 제목과 같은 X로 글이 시작한다(여백 없음). 일정 제목이 같은 줄에 있을 때만 엔진이 남겨 준 오른쪽 구간으로 물러난다. 묶음(overflow)은 "○── 거래 N건 · 합계" 한 줄(합계가 오해를 부르면 종류별 건수). 연결/대략 시각은 점선, 연결은 작은 링크 마크. 배경 카드·칩 없음. 일정 위에 겹치면 페이지 색 헤일로로만 가독성을 확보한다.
- 이름이 들어갈 자리가 좁으면(좁은 열, 큰 글자) 이름을 빼고 금액만 쓴다.
- 시간 표시는 단계적으로 생략: 거래 요약이 제목 줄에 있거나 줄이 시작 시각 자리를 덮으면 시작 시각, 줄이 끝 시각 자리를 덮거나 높이가 부족하면 종료 시각을 뺀다.
- 엔진이 제목을 줄이라고 한 경우(`abbreviated`/`cramped`)에만, 그리고 실제로 그려진 줄이 제목 줄과 겹칠 때에만 제목 폭을 제한한다(`EventItem.titleMaxWidth`).
- 엔진 변경: 묶음 행 높이(`overflowCard`) 28 → 20(글 한 줄). 거래 줄 높이(24)와 폭 비율은 그대로(기존 터치 테스트가 의존).
- 합성 fixture: `-demo -demo-txn`(전체), `-demo -demo-txn-lite`(여유 있는 화면). 배치와 터치 영역은 `DayRenderPlan` 그대로다.

### 거래 행: 카테고리 아이콘, 제목 숨김, 헤더 연결

- 거래 행은 일정 제목보다 아주 조금(약 11pt) 들여 쓰고, 소비 카테고리가 분류된(`classified`) 거래는 점 대신 카테고리 아이콘(`CategoryIcon`)을 쓴다. 미분류/모름/기타는 점. 카테고리는 추측하지 않는다: `AllocationItem.categoryID`(배분의 분류)와 `TransactionMarkerItem.categoryID`(배분들이 한 카테고리로 일치할 때)만 쓴다. 분류 체계(canonical taxonomy) 목록이 아직 없어 id의 단어(영·한)로 아이콘을 고르고, 맞는 게 없으면 태그 아이콘.
- 일정 제목에 거래가 실제로 걸리고 외부 헤더도 쓸 수 없으면(엔진이 제목을 줄이라고 한 경우) 제목을 그리지 않고 거래를 보여 준다.
- 외부 헤더가 있는 카드는 위쪽 모서리를 각지게 하고 왼쪽 띠를 같은 색·같은 두께로 이어, 헤더와 카드의 옆선이 끊기지 않는다.
- 일정 시간 안에 있지만 그 일정의 소비가 아닌(연결 안 된) 거래는 독립 행으로, 일정 카드 위에 겹쳐 글로만 그려진다(배경 없음).
- `-demo-txn` 데모는 일부 거래를 분류해 아이콘을 보여 준다(DemoLinks.classify).

### 거래 행의 선: 점 → 선 → 아이콘/글, 꺾인 선

- 거래 행은 날짜 열 왼쪽 가장자리의 점(●, 거래가 일어난 정확한 시각)에서 가는 선(──)이 아이콘 칸/글까지 이어진다. 글은 작은 마진(약 25pt) 뒤에서 시작하고 아이콘 칸은 항상 비워 두어 모든 행의 글이 같은 X에 선다.
- 글이 정확한 시각에 있지 않으면(다른 줄과 겹치지 않게 밀렸거나, 아래 경우) 선이 꺾여서 점은 정확한 시각에, 글은 정돈된 줄에 놓인다(`LineItem.anchorY`).
- 제목이 거래 때문에 그려지지 않은 일정에서는 그 거래가 제목 줄 자리로 올라와 카드 위쪽에 가지런히 쓰이고, 선이 거래 시각에서 그 줄로 꺾인다.

### 외부 헤더: 작은 탭

- 헤더는 카드 왼쪽 위에 얹힌 작은 탭이다: 글자 폭만큼만(카드 폭 안), 높이 22 → 16(`headerRow`), 글자 10pt(medium, 약간 옅게), 위 모서리만 둥글고 아래는 카드의 위쪽 경계선과 맞닿는다. 카드 본문과 같은 색 계열이지만 한눈에 구분된다.
- 헤더에는 시각을 쓰지 않는다. 시작 시각은 카드 오른쪽 위에 둔다(거래 줄이 그 자리를 덮으면 생략).

### 요약은 정보, 일정 안 여러 거래는 정렬된 줄 + 꺾인 선

- 요약("거래 N건 · 합계")은 특정 시각이 아니므로 점/선 없이, 일정 글과 같은 X에서 시작하는 정보 글로만 쓴다.
- 일정 안에 거래가 여러 개 보일 때(`insideRows`), 각 줄은 카드 왼쪽 가장자리의 점(거래의 정확한 시각)에서 선이 꺾여 줄의 글로 이어진다. 글은 일정 밖 거래 행과 같은 위치(아이콘 칸 포함)에서 시작해 한 열로 정렬된다. 시각 좌표는 `EventItem.insideAnchors`(같은 `DayRenderPlan`).
- 카테고리 아이콘은 분류된 거래에만 붙는다. 카테고리는 배분(allocation)에 저장되므로 배분이 없는 거래(일정에도 활동 외로도 정해지지 않은 거래)는 아이콘이 없다. 데모는 거래 일부를 분류해(`DemoLinks.classify`) 일정 안/밖 모두에서 아이콘을 보여 준다.

### 날짜 이동 중 들어오는 날의 일정 (겹침·잘림 방지)

- 이동 중에는 지금 화면의 공유 시간축을 그대로 쓴다(드래그 중에도, 가로 이동이 끝날 때까지도). 새 날짜의 AdaptiveLayout로의 시간축 보간은 가로 이동이 끝나 `moveTo`가 확정된 뒤 기존 축 전환(`publishAxisChange`)이 한다. 드래그 취소/방향 반전은 `swipeOffset`을 0으로 되돌릴 뿐 축을 건드리지 않아 원래 화면과 픽셀 단위로 같다(스크린샷 바이트 비교로 확인).
- 엔진이 배치하지 않은 날(`role == nil`)은 `DayRenderPlan`이 같은 시간→Y 좌표계에서 그린다. 일정의 시작·끝 Y는 그대로 두고(최소 높이 24로 늘리지 않음, 최소 3pt), 높이가 모자란 만큼 내용만 줄인다(행 → 시간 → 제목).
- 제목이 서로 겹치거나 높이가 모자라 못 쓰는 일정 무리(세로로 가까운 2개 이상)는 "일정 N개" 하나로 요약하고, 일정 카드는 실제 시각의 얇은 막대로 남는다(`Summary.countOnly`). 여유 있는 일정은 카드·제목 그대로다.
- 거래 줄은 지금처럼 텍스트 행이며, 시각과 글 위치가 다르면 선이 꺾인다. 표시 축약은 화면 그리기뿐이고 일정·거래 데이터는 바뀌지 않는다.
- 합성 fixture: `-demo -demo-trans` (조용한 오늘, 전날/이틀 뒤의 아침 짧은 일정 무리, 바쁜 내일 오후, 사흘 뒤 하루 종일).

- 이동 후 시간축이 보간되는 동안(`editor.transition != nil`)에는 지금 주인공이 된 날도 같은 규칙으로 그린다(`DayRenderPlan(settled: false)`): 엔진 결정은 목표 축 기준이라, 보간 중인 축에서는 제목이 서로 겹쳐 보였다. 제목 충돌은 앞 카드가 아직 덮고 있는지와 무관하게 제목 줄끼리의 겹침으로 판단한다(`titlesOnly`): 연달아 있는 짧은 일정은 카드가 서로 닿지 않아도 제목 줄이 겹친다. 높이가 자라 각자 제목 줄(≈19pt)을 가지면 요약이 풀리고 카드·제목이 나온다.

### 카드를 줄 수 없는 일정: 막대 + 라벨 (색 구분)

- 이동 중이거나 시간축이 바뀌는 동안(`incoming`) 제목 한 줄(≈19pt)을 담을 높이가 없는 일정은 카드를 그리지 않고 실제 시작·끝 Y의 얇은 막대(`EventMarkerBar`, 캘린더 색)로 그린다. 시간이 겹치는 막대는 나란한 줄(lane)에 놓여 포개지지 않는다.
- 막대 묶음 오른쪽에 라벨 하나: 일정 한 개면 제목, 여러 개면 일정마다 자기 캘린더 색의 점과 "일정 N개". 라벨을 누르면 일정 목록에서 고른다. 다른 색 일정도 막대 색과 점 색으로 구분된다.
- 여유 있는 이웃 일정은 카드·제목 그대로이며, 막대가 된 일정은 제목 배치에서 빠져 이웃의 제목이 밀리지 않는다. 높이가 자라 제목 줄이 생기면 막대가 카드로 바뀐다.

- 막대는 공간이 자라면 카드로 **펼쳐진다**(`EventItem.openness` 0→1, smoothstep): 폭이 자기 줄(lane)에서 카드의 자리·폭으로, 색이 진한 막대색에서 옅은 카드색으로, 모서리·테두리·제목이 차례로 나타난다. 제목 줄 높이에 도달하는 순간의 모습이 실제 카드와 같아서 막대가 사라지고 카드가 생기는 교체가 없다. 라벨("일정 N개")은 펼쳐지는 만큼 옅어진다.

### 짧은 일정 바로 뒤의 일정 (최소 높이가 만드는 가짜 겹침)

- 엔진은 일정을 최소 15분 길이로 보기 때문에, 20:00–20:10 일정과 20:10에 시작하는 일정이 "겹친다"고 보고 뒤 일정을 한 단계 들여 쓰게 했고, 짧은 카드의 최소 높이(24pt)가 뒤 일정 위로 올라탔다.
- 그리기(`DayRenderPlan`)에서는 들여쓰기를 **실제 시각**으로 판단하고(`realOverlap`), 최소 높이로만 뒤 일정에 닿는 카드는 뒤 일정의 시작 직전에서 멈춘다(자기 실제 끝보다 짧아지지는 않는다). 실제로 겹치는 일정은 그대로 들여 쓴다. 엔진의 배치·요약 결정은 바꾸지 않았다.

- 펼쳐지는 막대는 제목 줄 높이의 절반쯤(t≈0.5)까지는 막대(라벨이 이름을 말해 줌)로 남고, 그 뒤 짧은 높이 구간(t 0.5→0.8)에서 카드 폭으로 열리며 제목이 들어온다. 이름 없는 띠나 폭이 제각각인 막대가 보이지 않는다. 제목은 항상 카드 크기로 잘려 카드 밖으로 나가지 않는다(`EventMarkerBar`는 크기를 먼저 정한 뒤 클립한다).
