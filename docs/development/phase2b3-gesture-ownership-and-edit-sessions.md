# Phase 2B-3 — 고정 그리드의 제스처 소유권과 편집 세션 기반

대상: `-browse-temporal`(DEBUG) 고정 그리드 Browse. 이번 단계는 **편집을 연결할 기반**만 만든다. 생성·이동·리사이즈 UI, Draft, EventKit 쓰기는 없다(`TimelineEditor`·EventKit 경로 변경 없음). 기본 Browse·Release 동작, 고정 N칸, 핀치·날짜 이동은 그대로다.

## 1. 제스처 소유권 (`FixedGrid/FixedGridGestures.swift`)

터치가 **시작되는 곳**과 **현재 모드**로 한 번에 소유권을 정한다. 이 판단은 순수 함수라 테스트로 검증한다. 날짜 이동의 상태 머신은 여전히 `DayMoveModel` 하나뿐이다.

| 시작 위치 | browse | editing (일정 선택됨, 이번엔 DEBUG 프로브만) |
|---|---|---|
| 선택된 일정의 핸들 | — (browse에는 핸들 없음) | 핸들 드래그, 핸들 탭 **만** |
| 일정·거래선·묶음 카드 | 탭(정지 시 선택), 길게 누르기, 날짜 스와이프, 스크롤, 핀치 | 탭(향후: 다른 일정 선택), 스크롤, 핀치 |
| 빈 격자 | 길게 누르기, 날짜 스와이프, 스크롤, 핀치 | 탭(향후: 편집 종료), 길게 누르기(향후: Draft 생성), 스크롤, 핀치 |
| 시간 거터 | 날짜 스와이프, 스크롤, 핀치 | 스크롤, 핀치 |

- **실행 중인 제스처가 막는 것** (손가락이 모두 떨어질 때 또는 해당 제스처가 끝날 때까지):
  - 핀치: 한 손가락 제스처 전부(남은 한 손가락이 스크롤·스와이프·탭을 시작하지 못하고, 진행 중이던 길게 누르기는 취소됨)
  - 길게 누르기: 스크롤·스와이프·탭(두 번째 손가락이 오면 핀치로 넘어감)
  - 핸들 드래그: 나머지 전부
  - 날짜 스와이프: 스크롤·탭·길게 누르기·핸들(핀치는 여전히 인계 가능)
- **편집 중:** 날짜가 움직이지 않는다(분할을 고정하므로). 핸들에서 시작한 드래그는 어느 방향이든 스크롤·날짜 이동·핀치가 되지 않는다.
- **탭의 의미:** 정지 상태에서만 센다. 이동 중인 날짜에 손가락이 닿으면 이동을 멈추는 기존 즉시 인계가 그대로 동작한다. browse의 길게 누르기는 안내 문구 강조(기존 동작)이고, 향후 의미(`createDraft` / `edit(id)`)를 함께 반환한다.

## 2. SwiftUI/UIKit 경쟁 정리 (`PinchZoomScrollView`)

- 고정 그리드 콘텐츠의 SwiftUI `.onTapGesture`·`.onLongPressGesture`를 없앴다. 탭·길게 누르기(0.6초, 이동 허용 10pt)·핸들 드래그는 핀치·날짜 스와이프·스크롤과 **같은 컨테이너의 UIKit 인식기**가 되어 UIKit 하나가 조정한다.
- **터치 시작 시 결정** (`gestureRecognizer(_:shouldReceive:)`): 시작 지점의 hit(`DayRenderPlan.hit`, 그리드의 단일 hit test)와 모드로 `FixedGridGestures.receives`를 묻는다. 받지 않는 인식기는 그 터치를 아예 추적하지 않으므로, 다른 인식기를 기다리게 하지 않는다(`EditGestureHost` 패턴).
- **핸들 드래그 우선:** 스크롤 pan, 날짜 스와이프, 핀치는 핸들 드래그가 실패하기를 기다린다(`shouldBeRequiredToFailBy`). 핸들 드래그는 핸들에서 시작한 터치만 받으므로, 핸들 밖 터치에서는 기다림이 생기지 않는다.
- **차단 일원화:** 핀치 전용이던 `suppressed` 플래그를 `holds`(실행 중 인식기 → 막는 집합)로 바꿨다. 막는 것은 `isEnabled = false`이고, 이 상태가 진행 중인 제스처를 취소한다. 손가락이 모두 떨어지면 전부 풀리고, 1.5초 안전장치도 유지했다.
- **DEBUG 프로토타입 격자:** `RenderGridScreen`은 hooks가 `nil`이라 새 인식기가 없고 동작이 이전과 같다.

## 3. 편집 세션 freeze / unfreeze (`FixedGridBrowseModel`)

- `freeze(position:bounds:windows:zoomKey:inputs:baseline:) -> id`:
  - 그 순간 그려진 공유 분할과 해당 창들의 엔진 결정을 고정한다. 세션은 한 번에 하나이며, 이미 열려 있으면 같은 id를 돌려준다.
  - 고정 중 `shared`는 데이터·줌·계획과 무관하게 고정 분할을 돌려준다. 회전 시에는 같은 칸·시각에 높이만 바뀐다.
  - 고정 중 `decisionForDrawing`은 줌이 바뀌어도 고정 결정을 돌려주고, 엔진은 돌지 않는다.
  - 날짜 읽기·reload·prefetch·캐시 변경·백그라운드 분할 계획은 **계속 일어난다**. 그 결과는 세션이 끝나면 쓰인다.
- `unfreeze(id)`:
  - 고정 분할에서 지금 계획된 분할로 0.3초 ease-out 보간한다. 첫 프레임은 고정 분할과 같다.
  - `thawing(window:)`로 고정 결정에서 현재 결정으로 같은 시간 동안 교차 페이드한다(2B-2의 `blend` 재사용).
  - 정지 상태라면 화면 가운데 시각을 `AnchorState`로 유지한다(확대 시).

## 4. 원본 revision 경계 (`FixedGrid/FixedGridEditBaseline.swift`)

세션을 열 때 원본을 찍고, 세션 동안 갱신하지 않는다.

| 경계 | 의미 |
|---|---|
| `dataGeneration` | reload(캘린더가 바뀌었을 수 있음). 움직였다면 같아 보이는 날도 다시 읽혔을 수 있다 → `reloaded` |
| `dataRevision` | 보관 중인 날이 추가·교체·제거됨. 움직이지 않았으면 아무것도 비교하지 않는다(비용 0) |
| `days` | 세션 시작 시 화면 창의 날짜들. 지금과 다르면 `changedDays`, 지금 캐시에 없으면 `unknownDays`(변경으로 보지 않음) |
| `target` | 선택한 일정. 캘린더 키(`eventKey`)로 찾고 revision token·시작·끝을 비교해 `unchanged` / `changed` / `gone` / `unknown` |

`changes(dataGeneration:dataRevision:timelineFor:)`는 충돌이 있는지와 그 위치만 알려 준다. 저장·충돌 해결은 이번 범위가 아니다.

## 5. 검증

- **`OnAllAppTests/FixedGridEditFoundationTests.swift` (8개):**
  - 모드·시작 위치별 소유권 표 전체
  - 핸들은 편집 중 선택된 카드에만 있고, 잘린 끝에는 없음
  - 실행 중 제스처의 차단 집합(핀치 중 한 손가락 잔류 → 모두 차단, 길게 누르기 취소)
  - 탭·길게 누르기 의미(이동 중 탭 무시)
  - **freeze 동안 데이터 변경과 백그라운드 계획이 진행되고**, 분할·결정은 그대로, 줌 키 5종에서 엔진 0회, 회전 시 높이만 변경, 원본 대비 변경일 감지
  - **unfreeze 시** 첫 프레임 = 고정 분할, 18프레임 안에 정확히 현재 계획, 프레임당 이동 ≤ 전체의 1/5, 3× 줌에서 가운데 시각 오차 < 1e-6분, 이후 결정 복귀
  - 원본 경계: reload·변경일·대상 이동·삭제·미보관 구분
  - 실제 `AppModel`에서 freeze 중 prefetch·reload가 날짜를 바꾸고 원본이 `reloaded`를 감지
- **시뮬레이터 실터치** (`-browse-temporal-edit-probe`, `docs/ui-reviews/browse-gestures/`):
  - 탭 → 일정 상세가 열림(UIKit 탭 경로)
  - 일정 길게 누르기 → 세션 시작, 핸들 표시, 원본 "외부 변경 없음"
  - 시작 핸들에서 **옆으로** 끈 드래그와 끝 핸들에서 세로로 끈 드래그 → 핸들 드래그 2회(10단계), **날짜 이동 없음**
  - 편집 중 빈 곳 가로 스와이프 → 날짜 그대로
  - 핸들 탭 1회 집계, 빈 곳 탭 → 세션 종료, 이후 browse 스와이프는 날짜를 이동
  - 세션 중 핀치 확대와 세로 스크롤 동작, 핸들이 확대된 카드를 따라감
- **기존 탐색 회귀** (2B-2 커밋을 따로 빌드해 같은 세션에서 번갈아 각 5회):

  | 스크립트 | 2B-2 | 2B-3 | 비고 |
  |---|---|---|---|
  | swipes | 31/3476 (0.89%) | 16/3489 (0.46%) | 경계 턴 12.1 → 11.6 ms |

  지연 차이는 표본 잡음 범위이며 회귀는 없다. 원자료는 `measurements/`.

## 6. 남은 편집 설계 문제

- **핸들 드래그의 실제 의미:** 15분 스냅, 고정 축 위 좌표 ↔ 시각 변환(`ElapsedMinuteAxisMapping`), 화면 가장자리 자동 스크롤, 드래그 중 줌 금지 여부(지금은 핸들 드래그 중 핀치 차단).
- **Draft 모델:** 이벤트 id와 실제 시작·끝(자르지 않은 값)을 기준으로 두 열에 투영. 자정 넘김 일정의 핸들은 지금 `continuesFromPreviousDay/ToNextDay`로 잘린 쪽을 끄는데, "하나의 이벤트" 계약에 맞게 다른 열의 실제 끝에 핸들을 두도록 바꿔야 한다.
- **빈 곳 길게 누르고 드래그로 생성:** 지금 browse의 길게 누르기는 안내 강조다. 생성 진입을 browse에서 할지 편집 모드에서만 할지 UX 결정이 필요하다(0.6초 대 기존 편집기 0.3초 포함).
- **세션 중 외부 변경 처리:** `Changes`는 감지만 한다. 대상 `gone` / `changed`일 때의 UI(Draft 유지·폐기·병합)와 저장 직전 재검증이 남았다. `reloaded`인데 내용이 같은 경우를 어떻게 다룰지도 정해야 한다.
- **세션 중 선택일 외부 변경**(주간 스트립, "오늘")은 지금 세션을 끝낸다. Draft가 있을 때 확인을 받을지 결정이 필요하다.
- **해제 시 결정 교차 페이드:** 저장 직후 새 분할로 돌아갈 때 편집한 가장자리 시각을 고정해야 한다(지금은 화면 가운데 시각 고정).
- **VoiceOver:** 탭이 UIKit으로 옮겨졌다. 카드의 기본 동작은 SwiftUI 접근성 라벨로 유지되지만 실기기에서 확인하지 않았다. 편집 핸들의 접근성 동작도 정의가 필요하다.
