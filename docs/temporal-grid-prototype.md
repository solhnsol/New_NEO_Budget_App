# Adaptive Temporal Grid 프로토타입

브랜치 `feat/fixed-temporal-grid-prototype` (기반: `feat/render-normalization` 최신, `fixedAxis`·`AdaptiveLayoutEngine`·`EventPresentation`·`AxisStabilizer`는 이미 포함되어 있어 새로 만들지 않았다). Browse 화면·EventKit·금융 원장·제스처·Focus Mode·기존 4일 스무딩은 건드리지 않았다. 변경은 `Timeline/TemporalGrid/` 신규 파일, `OnAllApp.swift`의 DEBUG 분기 한 줄, 테스트 4개 파일, 이 문서뿐이다.

한 줄 결론: **고정 칸 모델은 날짜 이동 안정성(Y 이동 −66~−83%)과 "정보가 몰린 곳이 확대된다"는 점에서 실제로 유망하다. 그러나 글자 크기가 크거나 viewport가 작거나 일정이 매우 많은 날에는 기존 방식보다 분명히 나쁘다**(10절). 제품 채택 전에 해결할 문제는 11절.

## 1. 데이터 모델과 좌표계

`TemporalGridPartition` (`TemporalGridPartition.swift`, 순수 값 타입):

- `boundaries: [Double]` — N+1개의 분. `[0] == 0`, `[last] == 1440`, 엄격 증가. 계획된 분할은 정수 분, 보간된 분할만 소수 분을 갖는다(`wholeMinuteBoundaries`로 확인).
- `totalHeight` = `viewportHeight × zoomScale`, `slotHeight = totalHeight / N` (모든 칸 동일).
- 칸 i 안은 선형: `y(m) = i·h + (m − b[i])/(b[i+1] − b[i])·h`. 경계 시각은 뒤 칸에 속하고 24:00은 마지막 칸.
- `timeToY(minute)` / `yToTime(y)`는 정확한 역함수(테스트: 0.37분·0.73pt 간격 왕복 오차 < 1e-9, zoom 2.5 포함). 일정 높이는 `y(end) − y(start)`이며 글자 때문에 늘리지 않는다.
- `zoomed(viewportHeight:zoomScale:)` — 경계는 그대로, 높이만 같은 비율(zoomScale ≥ 1로 clamp).
- `interpolated(from:to:progress:)` — 경계별 `(1−p)A + pB`, 반올림 없음. 두 분할의 최소 칸 길이가 10분 이상이면 모든 p에서도 10분 이상이다(볼록 결합).
- 개별 입력 상태는 `TemporalGridParameters`(칸 수, 후보 단위, 최소/최대 구간, 날짜 가중치, 모든 비용 가중치)와 `GridDayEntities`(정적 엔티티)로 분리.

**기존 `TimelineAxis`/`fixedAxis` 어댑터** `timelineAxis()`: 계획된(정수 분) 분할은 정확히 변환된다(칸 N개 세그먼트, 오차 0, 엔진에 `fixedAxis`로 넣어 레이아웃이 그 축을 그대로 쓰는 것을 테스트). **정밀도 분석**: `TimelineAxis.Segment`는 `Int` 분이고 `y(minute:)`도 `Int`를 받는다. 보간 중 경계는 소수 분이라 이 계약에 담으면 정수 분으로 반올림되어 최대 반 분 높이(최대 2.6pt, 8시간 칸에서는 0.06pt)만큼 틀리고 한 분 높이씩 계단처럼 움직인다. 그래서 보간·배치는 파티션 자체에서 `Double`로 하고 어댑터는 정지 상태 전용으로 뒀다(`maximumError`로 오차 보고, 테스트). 정밀도를 `TimelineAxis`로 유지하려면 `Segment`를 `Double` 분(또는 1/60분 정수 단위)으로 확장해야 하며, 이는 타임라인 전체가 쓰는 계약 변경이라 이번에 하지 않았다.

## 2. 분할 최적화 알고리즘

`TemporalGridPlanner` — 후보 경계(5분 배수, 289개) 위의 동적계획법.

- 상태: `cost[k][j][c]` = k개 칸으로 0..j를 덮고 마지막 칸의 길이 등급이 c일 때 최소 비용. 길이 등급은 반옥타브(10분=0 … 8시간=11)이며 한 등급 차이까지는 무료. 다음 등급별로 "이전 최선 등급"을 먼저 접어 두어 작업량은 `N × 위치 × (등급² + 길이)` ≈ 백만 회. 전수조사 없음. 동률은 고정 순서로 풀어 같은 입력 → 같은 분할(역순 입력·캐시 상태·다른 창을 먼저 계획한 경우에도 같음, 테스트).
- 칸 하나의 비용은 `(시작, 길이)`로만 정해지므로 계획당 한 번 표로 만든다. 요구량은 1440분 해상도로 미리 집계(질량 prefix sum).
- **제약**: 칸 수 정확히 N, 길이 10분~8시간. 해가 없으면(`N·최소 > 1440` 또는 `N·최대 < 1440`) 가장 가까운 가능한 값으로 **완화하고 `constraintsRelaxed`로 알린다**(테스트: N=2 → `[0,720,1440]`, N=200). 후보 5분은 탐색 해상도일 뿐이다: 일정·거래 시각은 반올림되지 않고 `y()`가 17분·5분을 정확히 계산한다(테스트).
- **요구량(Temporal Demand)** — 하루마다 한 번 `TemporalDemandProfile`로 계산해 캐시하고, 창(D−1, D, D+1, D+2)에서 가중치로 합친다.

| 종류 | 의미 | 요구 |
|---|---|---|
| A,B 짧은 일정(≤2시간) | 제목 식별 | 구간 전체 높이 ≥ 제목 전체 표시 높이(25pt, `EventPresentation`의 titleNeed+ramp) |
| A,C 긴 일정 | **시작·종료 각 30분**만 | 같은 높이. 길다는 이유로 전체 구간에 해상도를 주지 않음 |
| E 일정 내부 연결 거래 | 거래 행 | 연속한 두 거래 사이 ≥ 행 높이 |
| D 독립 거래 | 인접 두 거래가 모두 글자로 보임 | 엔진의 `mergeableLinks`·pitch 재사용 |
| P0 존재 | 모든 일정이 최소 선(4pt) | **날짜 가중치를 곱하지 않음** |
| F 빈 구간 | 요구 없음 → 길게 압축 | |

- 비용 = 가중 claim 부족분 + 혼잡(칸 안 항목 질량²) + 정각 선호(30분 0.02, 15분 0.04, 그 외 0.07) + 길이 등급 변화 + 일정 경계 정렬 보상(−0.04). 가중치는 전부 `TemporalGridParameters` 한 곳에 있다. 날짜 가중치 D−1/D/D+1/D+2 = 0.25/1.0/0.8/0.25는 선호 claim에만 곱하고 `presence`에는 곱하지 않는다(테스트).
- 칸 하나가 다른 칸 구간에 걸치는 claim은 겹친 시간 비율로 각 칸에 배분한다(근사, 12절의 한계 참조). 한 칸의 최대 해상도로도 만족 못 하는 claim(예: 3분 간격 두 거래가 26pt)은 탐색에서 제외하고 `unservableClaimCount`로 보고한다.
- **정각 선호가 가독성을 해치지 않음**: 후보 5분 탐색의 claim 비용(실제 높이 기준)이 60분만 쓴 탐색보다 나쁘지 않다(20개 fixture 전부, 테스트). 빈 날은 전부 정각(2시간 칸 12개), 15분 일정이 연속된 날은 15분 경계가 생긴다.
- 정적/동적 분리: `GridDayEntities`(일정·거래의 실제 분, 한 번 생성) + `GridPlacement.place`(y와 `EventPresentation`만 계산, 겹침 분석 없음).
- 캐시 `TemporalGridStore`: 프로필과 분할을 내용·크기·설정 해시로 보관, 한도 초과 시 오래된 것부터 폐기. 줌·프레임·스크롤은 키에 없다.

## 5. 날짜 전환 시 안정성

- 두 분할을 사전 계산(캐시), 프레임마다 경계 선형 보간만. 테스트: p=0은 A와 동일, p=1은 B, p=0.5는 정확히 중간값, 모든 p에서 경계 증가·가로줄 y 고정·totalHeight 불변·칸 수 불변, 일정 위치가 연속(p를 1%씩 움직일 때 한 프레임 최대 이동 < 8pt), 일정의 시간 순서 불변. 101프레임 동안 최적화·프로필 계산 0회.
- 한 칸 이동 시 프로필 1개(4개 중 3개 재사용)와 분할 1개만 새로 계산(테스트).
- 시간 라벨은 A·B 라벨 교차 페이드(`trans-p0.5.png`처럼 중간 프레임에서는 두 라벨이 겹쳐 보인다). 이 겹침이 읽기 좋은지는 실기기 평가가 필요하다.

## 6. 일정·거래 정보 가독성

테스트(전부 통과): 모든 fixture × N=10/12/16에서 모든 일정·거래 id가 정확히 한 번 배치되고 실제 시각과 `timeToY`가 같다(P0), 일정은 글자 때문에 늘어나지 않는다(5분 일정 = 8시간 칸에서 0.06pt, E0 선), 같은 분 거래는 같은 y에 놓여 접근 가능하다, 빈 날·하루 종일·분산·밀집·긴+짧은 겹침·메인/보조 시간대 불일치·거래 밀집·32개 일정·글자 3배 모두 유효한 분할이며 칸 수·구간 제약을 지킨다. 같은 N의 균등 분할보다 제목/거래 글자가 같거나 더 많이 표시된다(밀집 짧은 일정은 엄격히 더 많음).

접근 경로: 거래는 항상 실제 시각의 점으로 있고, 글자가 숨겨진 거래는 점 + 같은 위치 묶음 배지(×n, DEBUG 화면)로 접근하며 확대(최대 3배)로 글자가 열린다. 3배 확대로도 분리되지 않는 같은 분 거래는 지금 점 묶음 배지만이 접근 경로이며 **전용 목록 UI는 이 프로토타입에 없다**(11절).

## 7. 확대·축소 결과

- zoom=1: `totalHeight == viewport`, 24시간 전체가 화면에 맞는다. zoom>1: 모든 칸이 같은 비율로 커지고 경계 불변, 시간 순서 불변, 그 사이 최적화 0회(테스트 `zoomingNeverPlansAgain`). zoom<1은 1로 clamp. 확대 상태에서도 왕복 오차 < 1e-9.
- DEBUG 화면은 1.0~3.0배 슬라이더 제공(스크린샷 `dense-zoom2.png`, `busy-zoom3.png`).

## 9. 성능 측정

- 한 창 계획(프로필 4개 + DP): 최적화(-O) 빌드 **프로필 0.2ms, 창 합산 0.1ms, 탐색 1.7ms** (바쁨/한가 fixture, N=12, 88 claim). Debug 빌드는 순차 실행 ≈ 50ms, 테스트를 병렬로 돌리면 400–700ms까지 늘어난다(표의 Debug 값은 비교용이 아님). 기존 4일 계획기는 같은 조건 2–20ms.
- 캐시 적중 시 0.01–0.06ms. 캐시 항목 5개(프로필 4 + 분할 1)가 약 50–65KB(근사). 한도 기본 32, 초과 시 오래된 것 폐기(테스트).
- **프레임마다 재계산이 실제로 일어나는가**: 기존 `TimelineGridView`는 축 전환 중 `TimelineView(.animation)` 본문에서 `DayRenderPlan(...)`을 매 프레임 새로 만든다(코드 확인). 24일정·30거래 하루를 60프레임 동안 같은 방식으로 만든 결과 **`DayRenderPlan.init` 0.88ms/프레임**. 격자 방식의 프레임 작업(경계 보간 + y + `EventPresentation`)은 **0.05ms/프레임**이고 정적 엔티티 생성은 한 번(0.05ms). 격자 쪽은 프레임마다 최적화·프로필·겹침 분석 0회(테스트로 101프레임 확인). 기존 렌더러는 이번에 바꾸지 않았다(0.88ms는 현 기기에서 60fps 예산 16.7ms의 5%지만 일정이 많은 날과 두 열을 곱하면 의미가 있다).

## 11. 제품 채택 전 해결할 문제

1. **Dynamic Type/작은 화면**: 높이를 고정하는 모델과 직접 충돌한다. 큰 글자·작은 화면에서는 viewport를 넘는 `totalHeight`(기본 확대 > 1)를 계획에 쓰거나, 필수 스크롤 허용을 도입해야 한다. 현재 zoom은 사용자가 조작하는 값이지 요구량으로 정해지는 값이 아니다.
2. **일정이 매우 많은 날**: 선으로 축약되는 일정이 생긴다. 확대/목록 같은 접근 경로의 실제 UI와 검증이 필요하다. (현재는 id 보존과 선택 영역은 보장하지만 전용 목록은 없다.)
3. **거래 밀집·같은 분 거래**: 오버플로 목록(기존 `TransactionOverflow` 개념)을 이 모델에 연결해야 한다.
4. **겹치는 일정**: 기존 `EventOverlapAnalysis` 들여쓰기를 붙여야 한다. 프로토타입 렌더링은 겹치는 일정 제목이 겹친다.
5. **`TimelineAxis` 정밀도**: 실제 스와이프에서 기존 렌더러를 쓰려면 `Double` 분 계약이 필요하다(1절).
6. **날짜 전환 애니메이션 라벨**: 교차 페이드가 읽기 좋은지 실기기 검증. 큰 경계 이동(최대 180분)이 나오는 날 쌍에서 위화감이 있는지.
7. **칸 수·가중치 튜닝**: 20개 합성 fixture의 소거 실험으로 고른 값. 실제 데이터 일주일 이상으로 재검증하고 N을 결정.
8. **설정/편집**: 시간 수정 제스처·Focus Mode·편집 중 분할 고정은 이 프로토타입 범위 밖이다(편집 중 `frozen` 분할 정책 필요). 기존 4일 스무딩은 유지했다.

## 렌더링 개선 (DEBUG 화면)

- **시간축**: 칸 배경 강조·점선 가로줄을 없애고 모든 가로줄을 같은 가는 실선으로 통일(y 고정). 시간 라벨 옆에 세로 압축 레일: ≤1시간 연속선 / 1~3시간 약한 점선 / >3시간 접힘(지그재그), 압축 칸은 `~끝시각 · 길이`를 함께 표시. 전환 중 레일은 A 스타일 → B 스타일로 페이드, 시간 라벨은 A가 앞 절반에 사라지고 B가 뒤 절반에 나타나(겹치지 않음, p=0.5는 라벨 없음) 보간된 임의 시각은 쓰지 않는다.
- **일정**: `EventPresentation` 그대로. 기존 `EventOverlapAnalysis`의 들여쓰기(최대 1단계, 레인·합치기 없음)를 하루당 한 번 계산(`GridDayEntities`). 제목·시간은 모든 카드 위 레이어에 그리고, `GridTextLayout`이 시간 순서대로 제목 → 거래 글자 → 시간 범위를 사각형 충돌 검사해 겹치면 글자만 숨긴다(카드·선 유지).
- **거래**: 점이 겹치는 묶음(간격 < 9pt, 묶음 높이 < 28pt)은 건수 배지로 표시하고, 탭하면 모든 거래의 ID·시각·금액을 보여 준다(금액은 실제 값, 이전의 가짜 금액 텍스트 제거). 확대로 공간이 생기면 묶음이 나뉘고 글자는 기존 reveal 규칙으로 복원. Dynamic Type ×3에서도 글자 사각형 충돌 없음(테스트).
- **테스트** `TemporalGridTextLayoutTests`: 모든 fixture × N=10/12/16 × 글자 ×1/2.2/3에서 쓰인 글자끼리 겹침 0, 모든 일정 카드와 거래 id 유지(묶음 합 = 독립 거래 수), 라벨 비중첩, 레일 경계값. 프레임당 비용(32일정): 0.04ms(Debug).
- **남은 문제**: 겹치는 일정이 많은 묶음에서는 제목이 일부 숨겨진다(카드는 유지). ×3 글자에서 거래 글자가 카드 위에 크게 놓인다. 거래 묶음이 거래 목록 UI로 연결되지는 않는다(탭 시 상태줄 표시만).
