# Correlator 설계안: 여러 알림을 한 금융 행위로 묶기

상태: **합의 완료 (2026-10-16)**. 7절의 결정에 따라 판정 규칙(`Sources/NEOBudgetCore/Correlation/NotificationCorrelator.swift`)을 구현했다. 처리 저장소에 적용하는 부분은 6절의 남은 일이다. 인계 문서(`handoff.md` 5.1)와 불변식 11·12를 따른다.

## 1. 왜 필요한가

10/2~10/8 실제 알림 재검증에서 Actual 소비 1,768,530원(51건) 중 파이프라인이 원장에 올린 것은 407,890원(22건)이었다. 빠진 금액의 대부분은 다음 세 가지이고, 셋 다 "이 알림이 다른 알림과 같은 돈인가"를 모르기 때문에 생긴다.

| 증상 | 7일 규모 | 지금 동작 | 원인 |
|---|---|---|---|
| 은행 출금 보류 | 5건, 1,338,140원 | `withdrawal` → `unsupportedEvent` 검토 | 체크카드 결제의 출금인지, 이체인지, 자동이체인지 모른다 |
| 이체 입금이 수입으로 | 5건, 52,104원 | `deposit`/`transferIn` → `income` | 내 다른 계좌에서 온 돈인지 모른다 |
| 환불 입금이 수입으로 | 4건, 52,922원 | `deposit` → `income` | 원거래 연결 단서가 없다 |
| 같은 결제의 여러 알림 | (Toss+카드+은행) | 중복 검사가 **뒤에 온 것을 보류** | 어느 쪽이 남는지가 도착 순서에 달려 있다 |

(교통카드 요금 24건은 10/16 파서 수정으로 해결됐다. 실제 데이터 재검증은 노트북에서 한다.)

Actual 최종 원장에서 알림↔거래 대응 모양은 1:1 64, N:1 7(여러 알림 → 한 거래), 1:N 12, N:M 19그룹(이체 양쪽)이었다.

## 2. 핵심 아이디어

Parser → Account resolution → **Correlator** → Assembler → Dedup → 원장 순서로, assembler 앞에 한 단계를 넣는다.

- Correlator는 아직 원장에 오르지 않은 draft들의 **집합**을 받아 "같은 금융 행위의 근거 묶음"(`Correlation`)을 만든다. 도착 순서가 아니라 집합에 대한 순수 함수다. 같은 집합이면 몇 번, 어떤 순서로 돌려도 같은 결과다.
- 묶음은 둘 중 하나다.
  - **확정(`confirmed`)**: 구조적 근거가 있다(3절). 한 원장 항목으로 자동 반영된다.
  - **제안(`suggested`)**: 금액·근접 시각만 맞는다. 원장에 자동 반영하지 않고 검토 대기열로 간다(불변식 11).
- 묶인 알림은 하나의 `LedgerEntry`가 되고 `evidenceIDs`에 모두 남는다. 어느 알림이 대표인지는 금액이 아니라 표시 정보(상호, 결제 수단)에만 영향을 준다. 금액이 서로 다르면 묶지 않고 충돌로 검토한다.

## 3. 구조적 근거 (이것이 이번 합의의 중심)

"금액과 시각이 같다" 위에 **계좌 계층이 이미 아는 사실 하나**가 더 있어야 확정이다.

| 짝 | 구조적 근거 | 예시 |
|---|---|---|
| 체크카드 승인 ↔ 은행 출금 | 체크카드 키와 출금 계좌 키가 **같은 등록 계좌**로 해소된다(레지스트리는 체크카드 제품 키를 그 카드가 결제되는 은행 계좌의 식별자로 이미 둔다) | 현대 체크 12,000원 승인 + 2초 뒤 우리은행 `NNNN-***` 12,000원 출금 → 지출 1건 12,000원 |
| Toss 결제 ↔ 카드 승인 | Toss가 말한 결제 수단(카드 제품)과 카드 알림의 수단 키가 같다 | Toss "현대카드 MM로 8,000원" + 현대카드 MM 8,000원 승인 → 지출 1건 |
| 이체 출금 ↔ 이체 입금 (양쪽 모두 내 계좌) | 출금 알림의 상대 키(은행+끝 4자리)가 입금 계좌의 등록 키와 같다 | 카카오페이 충전 "우리 1234" 50,000원 + 우리은행 1234 출금 50,000원 → 이체 1건 |
| 이체 한쪽만 도착 | 상대 키가 **등록된 내 계좌**로 해소된다 | 우리→토스뱅크 이체 출금만 왔고 상대가 등록된 토스뱅크 계좌 → 이체 1건(입금 쪽 알림 없음) |
| 환불 ↔ 원거래 | 원승인번호/원거래번호가 원거래의 번호와 같다 | 이미 구현(`originalApprovalReference`). 번호가 없으면 아래 "제안" |
| 카드대금 출금 ↔ 카드 부채 | 출금 문구의 카드사가 등록된 신용카드 하나로 해소된다 | 우리은행 "현대카드 결제 출금" 300,000원 → 카드 납부 1건 |

구조적 근거가 없는 경우의 기본값:

| 상황 | 기본 동작 |
|---|---|
| 금액·시각만 맞는 짝 (예: 아직 계좌에 연결 안 된 체크카드 + 출금) | **제안**으로 검토. 확인 한 번으로 그 카드 키가 계좌에 연결되어 이후는 자동 |
| 짝 없는 은행 출금 | 바로 "무엇의 출금인가요" 검토 항목. 나중에 짝이 오면 그 짝이 검토를 닫는다 |
| 짝 없는 입금 | 지금처럼 수입. 단 상대 이름이 내 계좌 키로 해소되면 이체 |
| 원번호 없는 환불 입금 | 같은 상호·같은 금액 이하의 최근 지출을 **제안**. 확인 전에는 수입도 환불도 아닌 대기 |

## 4. 도착 순서: 대기 창 없이 실시간 판정 (Q2 결정)

앱 안에서 처리하므로 **알림이 들어오는 대로 바로 반영**한다. 기다리지 않는다. 새 알림이 오면 이미 기록된 알림과 규칙으로 비교해 셋 중 하나로 판정한다(`CorrelationDecision`).

| 판정 | 뜻 | 예 |
|---|---|---|
| `corroborates` | 이미 기록된 행위의 근거다. 새 원장 항목을 만들지 않는다 | 승인이 먼저 반영된 뒤 온 은행 출금 |
| `newAct` | 새 행위다. 먼저 와서 검토를 기다리던 짝이 있으면 함께 닫는다(`closes`). 이체 한쪽이 수입으로 먼저 기록됐으면 그것을 이체로 바꾼다(`replacesIncome`) | 출금이 먼저 와서 검토 중일 때 온 체크카드 승인 |
| `suggests` | 금액·이름만 맞는다. 검토로 보내고 후보만 보여 준다 | 원번호 없는 환불 |

- 두 알림이 같은 행위로 묶이려면 시각 차이가 **짝 판정 허용 범위**(기본 10분, `matchToleranceMilliseconds`) 안이어야 한다. 이것은 기다리는 시간이 아니라 "얼마나 떨어진 알림까지 같은 행위로 볼까"의 기준이다. 실제로는 1~4초 간격이었다.
- 짝 후보가 여럿이면 시각이 가장 가까운 것, 같으면 ID가 작은 것을 고른다. 금액·계좌가 같은 후보끼리라 어느 쪽을 골라도 원장 금액은 같다.
- 어떤 순서로 도착해도 최종 묶음은 같다. 테스트가 모든 도착 순서(최대 4개 알림, 24가지)를 돌려 확인한다.
- 시각은 알림 시각을 쓴다.

## 5. 사용자 수정과 재평가

- 사용자가 묶음을 풀거나 직접 묶으면 그 결정이 `ManualOverride`로 남고, 재평가는 그것을 덮지 않는다(불변식 14).
- 새 증거(늦은 알림, 새 계좌 등록)가 오면 대기 중인 항목만 다시 판단한다. 이미 원장에 오른 항목은 근거 추가만 하고 금액·분류를 바꾸지 않는다.
- 확인 하나가 여러 항목을 푼다: 체크카드 키를 계좌에 한 번 연결하면 그 카드의 대기 중인 출금이 모두 풀린다(검토 대기열 설계 5.4와 이어짐).

## 6. 구현 상태

1. 완료: `NotificationCorrelator`(순수 판정 규칙)와 테스트 11개. 체크카드 승인↔출금, 여러 앱의 같은 결제, 이체 양쪽(카카오 충전↔은행 출금 포함), 수입으로 먼저 기록된 이체 입금, 환불 후보 제안, 같은 금액 실제 두 번 결제(묶지 않음), 모든 도착 순서.
2. 완료: 처리 저장소 적용. `CandidateProcessingRepository.process(_:observation:correlator:…)`가 저장된 후보들에 대해 판정하고 한 번에 적용한다. 근거만 되는 후보는 `corroborates`로 남고 원장을 바꾸지 않는다. 검토 대기 중이던 짝은 새 행위가 승격될 때 그 근거로 닫힌다(`needsReview` 상태는 그대로이고 `corroborates`가 있으면 닫힌 것으로 본다). 수입으로 먼저 반영된 입금은 새 원장 항목 종류 `reversal`(원래 항목의 정확한 반대 기록, 원래 항목은 남김)로 되돌리고 이체가 그 자리를 대신한다. 같은 알림을 다시 처리하면 처음 판정을 유지한다. 중복 검사(D003)는 근거 전용 후보를 행위로 세지 않는다. 테스트: 세 앱의 한 결제, 이체 양쪽, 카카오 충전, 환불 후보, 재처리, `reversal` 검증을 모든 도착 순서로.
   - D003에 따라 같은 계좌·같은 금액 결제가 5분 안에 같은 앱에서 두 번 오면 두 번째는 여전히 검토로 간다(판정 규칙은 두 행위로 보지만 저장소의 중복 검사가 더 보수적이다).
3. 남음: 계좌가 해소되지 않은 알림끼리의 금액·시각 짝 **제안**(3절 기본값 표 첫 줄). 지금은 해소 안 된 알림을 규칙에 넣지 않고, 계좌 확인 검토로만 보낸다.
4. 완료: 계좌 계층 연결. `CorrelationObservation(candidateID:draft:evidence:registry:fallbackSource:)`가 `resolve`로 계좌를, `resolveCounterpart`로 상대가 **등록된 내 계좌**일 때만 `transferCounterpart`를 채운다. 등록 안 된 상대(남의 계좌)는 비워 둔다.
6. 완료(코드, 실기기 확인 대기): 앱이 새 처리 경로를 쓴다. 단축어 동작 "알림 기록하기"가 알림 JSON을 받아 `ShortcutNotificationDecoder` → `NotificationIntake`(파서 → 계좌 근거 → 등록부 → 조립 → Correlator → 처리 저장소)로 넘긴다. 받은 알림과 계좌 설정(`IntakeSetup`)만 기기에 저장하고 원장은 `IntakeLedger`가 재생해서 만든다. 그래서 오늘 등록한 계좌가 그 전에 받은 알림까지 묶는다. 자세한 내용은 `docs/shortcut-intake.md`.
5. 완료(2026-10-16, 노트북): 실제 데이터(`data/`, 로컬 전용)로 10/9와 같은 7일 재검증. 알림 102건을 파서 → 계좌 해소 → Correlator → 처리 저장소로 순서대로 흘렸다. 계좌 확인 질문은 Actual 정답으로 한 번씩 답한 시뮬레이션이다(키 연결과 규칙 6개).
   - Actual 소비 51건 1,768,530원(10/9와 같은 기준) 중 원장 지출 42건 424,190원. 지출 항목 42건 모두 Actual 거래와 금액까지 일치하고, 정답에 없는 지출은 0건(10/9: 22건 407,890원). 늘어난 건수는 대부분 교통카드 요금이다.
   - 잘못 묶인 짝 0건. 근거로 묶인 알림 3건(체크카드 승인↔출금 1, Toss↔현대카드 2)이 모두 정답과 같은 행위다.
   - 남은 소비 9건 1,344,340원 중 은행 출금 5건 1,338,140원은 검토 대기다. 4건은 짝이 될 알림 자체가 없다(Q3대로 검토). 1건은 Toss "우리은행" 결제와 출금의 짝인데, Toss 쪽 계좌가 해소되지 않아(우리 계좌가 둘) 3번(해소 안 된 알림끼리의 제안)이 있어야 묶인다. 나머지 4건 6,200원은 요금 없이 잔액만 있는 티머니 "Trip in Progress" 알림이다.
   - 내 우리 계좌 두 개 사이 이체 5건 52,104원은 아직 입금은 수입, 출금은 검토로 남는다. 두 알림 모두 상대를 계좌 번호가 아니라 이름으로만 적어 구조적 근거가 없다. 환불 입금 등 실제 입금 5건 81,422원은 수입으로 맞다.
   - 열린 검토 15건: 계좌 확인 5(Toss), 무엇의 출금인지 10.
