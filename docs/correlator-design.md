# Correlator 설계안: 여러 알림을 한 금융 행위로 묶기

상태: **합의 전 초안 (2026-10-16)**. 아래 "결정할 것"(7절)의 답을 받은 뒤 구현한다. 인계 문서(`handoff.md` 5.1)와 불변식 11·12를 따른다.

## 1. 왜 필요한가

10/2~10/8 실제 알림 재검증에서 Actual 소비 1,768,530원(51건) 중 파이프라인이 원장에 올린 것은 407,890원(22건)이었다. 빠진 금액의 대부분은 다음 세 가지이고, 셋 다 "이 알림이 다른 알림과 같은 돈인가"를 모르기 때문에 생긴다.

| 증상 | 7일 규모 | 지금 동작 | 원인 |
|---|---|---|---|
| 은행 출금 보류 | 5건, 1,338,140원 | `withdrawal` → `unsupportedEvent` 검토 | 체크카드 결제의 출금인지, 이체인지, 자동이체인지 모른다 |
| 이체 입금이 수입으로 | 5건, 52,104원 | `deposit`/`transferIn` → `income` | 내 다른 계좌에서 온 돈인지 모른다 |
| 환불 입금이 수입으로 | 4건, 52,922원 | `deposit` → `income` | 원거래 연결 단서가 없다 |
| 같은 결제의 여러 알림 | (Toss+카드+은행) | 중복 검사가 **뒤에 온 것을 보류** | 어느 쪽이 남는지가 도착 순서에 달려 있다 |

(교통카드 요금 24건은 10/16 파서 수정으로 해결됐다. 실제 데이터 재검증은 노트북에서 한다.)

Actual 최종 원장에서 알림↔거래 대응 모양은 1:1 64, N:1 7(여러 알림 → 한 거래), 1:N 12, N:M 19그룹(이체 양쪽)이었다.

## 2. 핵심 아이디어

Parser → Account resolution → **Correlator** → Assembler → Dedup → 원장 순서로, assembler 앞에 한 단계를 넣는다.

- Correlator는 아직 원장에 오르지 않은 draft들의 **집합**을 받아 "같은 금융 행위의 근거 묶음"(`Correlation`)을 만든다. 도착 순서가 아니라 집합에 대한 순수 함수다. 같은 집합이면 몇 번, 어떤 순서로 돌려도 같은 결과다.
- 묶음은 둘 중 하나다.
  - **확정(`confirmed`)**: 구조적 근거가 있다(3절). 한 원장 항목으로 자동 반영된다.
  - **제안(`suggested`)**: 금액·근접 시각만 맞는다. 원장에 자동 반영하지 않고 검토 대기열로 간다(불변식 11).
- 묶인 알림은 하나의 `LedgerEntry`가 되고 `evidenceIDs`에 모두 남는다. 어느 알림이 대표인지는 금액이 아니라 표시 정보(상호, 결제 수단)에만 영향을 준다. 금액이 서로 다르면 묶지 않고 충돌로 검토한다.

## 3. 구조적 근거 (이것이 이번 합의의 중심)

"금액과 시각이 같다" 위에 **계좌 계층이 이미 아는 사실 하나**가 더 있어야 확정이다.

| 짝 | 구조적 근거 | 예시 |
|---|---|---|
| 체크카드 승인 ↔ 은행 출금 | 체크카드 키와 출금 계좌 키가 **같은 등록 계좌**로 해소된다(레지스트리는 체크카드 제품 키를 그 카드가 결제되는 은행 계좌의 식별자로 이미 둔다) | 현대 체크 12,000원 승인 + 2초 뒤 우리은행 `NNNN-***` 12,000원 출금 → 지출 1건 12,000원 |
| Toss 결제 ↔ 카드 승인 | Toss가 말한 결제 수단(카드 제품)과 카드 알림의 수단 키가 같다 | Toss "현대카드 MM로 8,000원" + 현대카드 MM 8,000원 승인 → 지출 1건 |
| 이체 출금 ↔ 이체 입금 (양쪽 모두 내 계좌) | 출금 알림의 상대 키(은행+끝 4자리)가 입금 계좌의 등록 키와 같다 | 카카오페이 충전 "우리 1234" 50,000원 + 우리은행 1234 출금 50,000원 → 이체 1건 |
| 이체 한쪽만 도착 | 상대 키가 **등록된 내 계좌**로 해소된다 | 우리→토스뱅크 이체 출금만 왔고 상대가 등록된 토스뱅크 계좌 → 이체 1건(입금 쪽 알림 없음) |
| 환불 ↔ 원거래 | 원승인번호/원거래번호가 원거래의 번호와 같다 | 이미 구현(`originalApprovalReference`). 번호가 없으면 아래 "제안" |
| 카드대금 출금 ↔ 카드 부채 | 출금 문구의 카드사가 등록된 신용카드 하나로 해소된다 | 우리은행 "현대카드 결제 출금" 300,000원 → 카드 납부 1건 |

구조적 근거가 없는 경우의 기본값:

| 상황 | 기본 동작 |
|---|---|
| 금액·시각만 맞는 짝 (예: 아직 계좌에 연결 안 된 체크카드 + 출금) | **제안**으로 검토. 확인 한 번으로 그 카드 키가 계좌에 연결되어 이후는 자동 |
| 짝 없는 은행 출금 | 대기 창이 끝나면 "무엇의 출금인가요" 검토 항목 |
| 짝 없는 입금 | 지금처럼 수입. 단 상대 이름이 내 계좌 키로 해소되면 이체 |
| 원번호 없는 환불 입금 | 같은 상호·같은 금액 이하의 최근 지출을 **제안**. 확인 전에는 수입도 환불도 아닌 대기 |

## 4. 도착 순서와 대기 창

같은 결제의 알림은 앱마다 1~4초 간격으로 온다. 그래서 짝이 될 수 있는 draft는 **대기 창**(제안: 2분) 동안 원장에 올리지 않는다.

- 창 안에 짝이 오면 함께 묶어서 한 번에 반영한다.
- 창이 끝날 때까지 짝이 없으면 혼자 반영한다(확정이면 원장, 아니면 검토).
- 창이 끝난 뒤 늦게 온 짝은 원장 금액을 바꾸지 않고 **기존 항목의 근거로만 추가**한다. 금액이 다르면 충돌 검토.
- 짝이 될 수 없는 draft(예: 등록된 신용카드 승인이고 같은 결제를 알리는 다른 앱이 등록돼 있지 않음)는 기다리지 않는다.

시각은 알림 시각을 쓴다. 캡처 시각만 있는 알림은 창 판정에 쓰되 확정 근거로는 쓰지 않는다.

## 5. 사용자 수정과 재평가

- 사용자가 묶음을 풀거나 직접 묶으면 그 결정이 `ManualOverride`로 남고, 재평가는 그것을 덮지 않는다(불변식 14).
- 새 증거(늦은 알림, 새 계좌 등록)가 오면 대기 중인 항목만 다시 판단한다. 이미 원장에 오른 항목은 근거 추가만 하고 금액·분류를 바꾸지 않는다.
- 확인 하나가 여러 항목을 푼다: 체크카드 키를 계좌에 한 번 연결하면 그 카드의 대기 중인 출금이 모두 풀린다(검토 대기열 설계 5.4와 이어짐).

## 6. 구현 범위 (합의 후)

1. `Sources/NEOBudgetCore/Correlation/`: `Correlation`(확정/제안, 구성 draft, 근거 종류), `Correlator` 프로토콜과 기본 구현. 순수 Swift, 시계·창 길이는 주입.
2. 계좌 계층은 바꾸지 않는다. Correlator는 각 draft의 해소 결과(같은 `AccountID`/`CreditInstrumentID`)와 상대 키 해소 결과만 읽는다.
3. Assembler가 묶음 하나를 원장 항목 하나로 만들도록 확장(`withdrawal`은 묶였을 때만 반영).
4. 합성 fixture: 표 3의 각 짝, 모든 도착 순서 순열, 늦은 짝, 금액 충돌, 30초 간격 같은 금액 실제 두 번 결제(묶지 않음), 사용자 분리 후 재평가.
5. 클라우드에서 `swift test`. 그 뒤 노트북에서 실제 데이터(`data/`, 로컬 전용)로 10/9와 같은 7일 재검증을 돌려 표 1의 수치를 다시 잰다.
